## §4 Deliverable 3 — Push-channel contract (binding for S2)

### Push-channel contract (binding for S2)

**Contract (technical-decided; the F-push adjudication) — SCOPED to the TS-core push channel (Node ≥20 + `tsx` resolvable):** on that channel the consumer push channel is **thin** and **never gates the consumer's own repo content**:

1. **Per-file lint is NOT re-run at push** — it is enforced earlier (edit-time ESLint + pre-commit `lint-staged`). A shipped-rule violation is blocked at edit-time + pre-commit + `npx eslint .`; CI is the backstop for a deliberate `--no-verify` bypass.
2. **Workflow-SECURITY/SYNTAX scanners (`actionlint`, `zizmor`) do NOT run on a consumer.** They are `owner: maintainer`. This is a deliberate **scope-OUT** (the framework does not lint a consumer's own workflows for supply-chain/syntax findings), NOT a "handed to another channel" claim: **that scanning of the consumer's OWN workflows is currently provided by no shipped channel** — neither this push hook nor any shipped CI template runs `zizmor`/`actionlint` (verified below). A consumer who wants action-pinning (`@v6` → SHA) enforcement adds it to their own CI.
   - **DISTINCT — the ci-tool-pinning unpinned-install gate stays `owner: 'both'`** (rework-round-3 correction). Its WORKFLOW population (`.github/workflows/*.yml`) is `ci-tool-pinning.md §2` pop 1 — "Scanned on every push, framework and consumer repos alike." So a consumer's own workflow carrying an **un-pinned bare** `run: pip install <pkg>` / `npm install -g <pkg>` IS flagged (narrow, deterministic, no-tool; §3 escape hatch `# ci-tool-pin: allow`). This is NOT the F-push case: F-push was the near-universal zizmor `unpinned-uses` `@v6` surface (blocks almost every real consumer's first push); Rule A fires only on the far-rarer un-pinned *tool install* and carries an escape hatch, which is why §2 deliberately keeps it on consumers. The gate's shell-script population (pop 2) remains framework-only (within-body `isFrameworkRepo`).
3. **The consumer push channel runs only:** framework enforcement-integrity that per-file pre-commit cannot see — rule-glob liveness, lint-staged binary resolution — plus offline link integrity on Markdown **changed in this push** (lychee, `both`, degrades if absent) — plus the deterministic ci-tool-pinning workflow pop-1 regex scan (above).
4. **A clean-tree `git push` is ALLOWED — on the TS-core channel.** ("Clean" excludes an un-pinned bare tool install in a workflow, which `ci-tool-pinning.md §2` intends to flag on any repo; the F-push `@v6` refs are NOT a Rule A violation and never block.)

**KNOWN-OPEN GAP (binding for S2 — do NOT inherit the guarantee as universal):** the "never gates the consumer's own content / clean-tree push allowed" guarantee holds **only on the TS-core channel**. The shipped dispatcher `packages/core/templates/shared/husky-pre-push.sh:30-34` falls to the bash fallback `packages/core/hooks/pre-push.fallback.sh` whenever `node --import tsx/esm -e ''` fails — its own comment (`:24-29`) names this as the **pnpm-monorepo layout where `tsx` lives in a sub-package**. This is a separate bash artifact outside S3's owner-split scope (different change-class than the F-push zizmor scan). Tracked as **issue #985**; S2's asserts must scope the thin-channel guarantee to the TS-core path and MUST NOT assert clean-tree-allowed on a `tsx`-unresolvable layout.

### F-push adjudication (against the S1 mandatory input)

**S1 F-push (report §2 R3 / §3):** the consumer pre-push ran a FULL zizmor audit over the consumer's OWN `.github/workflows/*.yml` and hard-blocked their FIRST `git push` on pre-existing `@v6` action refs (17 findings, `unpinned-uses`, rc=1).

- These are **consumer-repo-content scanners, not framework enforcement-integrity checks.** zizmor `unpinned-uses` + actionlint audit the consumer's ENTIRE pre-existing workflow set — content the framework never authored. - It is **robust to the literal F-push repro.** "Scope to the push diff" still blocks a first push to an empty remote (whole history in range → pre-existing workflows counted as added). "Not composed on a consumer" is unconditional.
- **Attention-is-not-a-mechanism compliant.** This is NOT "degrade to warn" (a warning nobody reads is not a mechanism, §1). It is an explicit scope-OUT: the framework does not security-audit the consumer's own workflows.
