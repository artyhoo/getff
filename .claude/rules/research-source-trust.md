## §1 The tier model

The full tier architecture, threat model, and cross-tier invariants are specified in the umbrella kickoff — **this rule points to that spec, it does not copy it** (single source of truth per [dual-implementation-discipline.md §7](dual-implementation-discipline.md)):

- [`.claude/orchestrator-prompts/rule-research-trust-tiers/kickoff.md` §4](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md) — target architecture: Tier 0 (builtin curated) → Tier 1 (derived from a direct dependency's local `homepage`/`repository` metadata, scope-locked, multi-tenant apexes ineligible) → Tier 2 (consumer-acked, `.ai-factory/research-allowlist.json`). First match wins.
- [`.claude/orchestrator-prompts/rule-research-trust-tiers/kickoff.md` §2](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md) — the calibrated threat model (H1 bar-lowering, H2 shared-host whole-host trust) that motivates the containments Tier 1 ships with.
- [`packages/core/research/allowlist-resolver.ts`](../../packages/core/research/allowlist-resolver.ts) — the implementation: `resolveAllowedSources(ctx)` + `validateProvenance(p, resolved, opts?)`.

One-line summary for readers who only need the shape: a provenance URL is authorized if its host matches a builtin key (Tier 0), OR derives from a direct dependency's own metadata scope-locked to that package and not a shared apex (Tier 1), OR is explicitly acked by a human in a committed, PR-reviewed file (Tier 2). Anything else fails closed.

## §2 The §4.5 re-tightening trigger

[Kickoff §4.5](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md) states, verbatim:

> The moment Path B (LLM code-gen) activates, Tier-1 auto-trust is downgraded to Tier-2-ack for any code-generating flow.

This is a **named, binding trigger**, not a suggestion: today's factory is deterministic and grammar-bounded (a wrong-but-well-formed lint rule is the worst case for a poisoned docs source, per [kickoff §2](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md) row 1). Tier 1's author-controlled trust (H1) is calibrated against that bound. If Path B ever ships — the factory starts emitting arbitrary AST-plugin code from research output — the blast radius of a poisoned Tier-1 host changes class (wrong rule → arbitrary code), and Tier-1's auto-trust for that flow MUST be downgraded to require an explicit Tier-2 human ack. Implementing Path B without also downgrading Tier 1 for its code-generating flows is a rule violation, not an oversight to catch later.

## §3 Anti-patterns

- **`#trust-by-name-not-scope`** — authorizing a research host because it belongs to a familiar-sounding package, without the accompanying same-package scope-lock. This is the T16 (`#pattern-matching-on-name`, [ai-laziness-traps.md §2](ai-laziness-traps.md)) shape applied to provenance: a package name matching what the researcher expects is not the same as `provenance.packageName === entry.package` actually holding. The resolver's Tier-1 branch enforces the scope-lock mechanically (`T-RTT-A`, cross-package provenance fails); this anti-pattern names the *reasoning* failure a reviewer or future author could still make by hand-authoring a provenance entry that skips the check's intent (e.g. copy-pasting an `allowlistKey` from a different package's entry because "it's basically the same ecosystem"). Counter: never derive trust from a package's *name similarity* — only from `entry.package` being the trusted, plan-builder-sourced identity that the resolver checks against `provenance.packageName`.
- **`#allowlist-as-code-not-data`** — extending research-source trust by editing framework TypeScript source (the pattern this umbrella replaced, [kickoff §1](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md)) instead of the appropriate **data** surface: Tier 1 is derived automatically from a consumer's own `package.json` + `node_modules` (no edit needed for a direct dependency with a single-tenant host), and Tier 2 extends via the committed `.ai-factory/research-allowlist.json` ack file — never via a source-code diff to `allowlist.ts` or `allowlist-resolver.ts`. Before this umbrella, a consumer researching an uncurated framework (e.g. Drizzle) hit `unknown allowlistKey` and had no path forward short of forking the framework's own source. Counter: a new trust grant is always a **data change** (an installed dependency's own metadata, or an acked JSON entry) — a PR that adds a host to `ALLOWED_SOURCES` or hand-writes a `multi-tenant-hosts.json` exception for a single request is the violation this names.

## §4 Ecosystem-prefix reservation (S4)

`Provenance.packageName` and `ResearchEntry.package` are bare package names today (implicit `npm:` ecosystem — the only adapter S1/S2 ship). This rule reserves, for a future S4, an **ecosystem prefix** on these names (triggered, not scheduled — trigger: first non-JS consumer request, first documented injection attempt, or Path B activation per §2 above). The concrete scheme (e.g. `cargo:serde`, `pip:requests`, with `npm:` remaining the implicit default for unprefixed names) is this rule's own forward-looking placeholder — **not** a kickoff-specified format: [kickoff §5 S4](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md) reserves the non-JS **adapters** (`{toolchain, stack}`), not a naming convention. This line reserves the placeholder now; S4 implements the parsing + `EcosystemAdapter` dispatch when triggered.

## §5 Defence-in-depth from the S2 adversarial review (items 1–3 documented-not-coded; item 4 now coded)

The S2 adversarial review (round 2) surfaced four residual observations against the resolver, each re-adjudicated in a 2026-07-03 follow-up (adversarial re-verification of every reachability claim). Items 1–3 were accepted **by design** rather than fixed with a code change — recorded here so a future auditor does not re-open them as new findings without checking this list first. Items 1–3 are prose-documented risk acceptances (not gated by principle 30 or any other CI mechanism), each with an explicit harden-criterion. Item 4 (round-1 B) has since been **coded** — its containment ships as a deterministic guard + paired-negative test (see the entry below).

1. **Union homepage ∪ repository trust (C).** Tier 1 trusts BOTH a package's `homepage` AND `repository` host — both enter the same `candidateFields` derivation in `resolveAllowedSources`'s `tier1For` and pass the *identical* filter chain (canonicalize → IP-literal → punycode → `isMultiTenantHost`) in one loop. By-design ([kickoff §4](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md)): a direct dependency is already trusted to run arbitrary install-time code on the consumer's machine, so trusting its self-declared hosts for *documentation research* is a strictly smaller grant than the trust already extended by `npm install`. **`repository` ⊆ `homepage` under the threat model:** both fields sit in the same attacker-controlled bucket (installed package metadata) and `extractHttpsHostFromMeta` resolves them identically — a poisoned `repository` and a poisoned `homepage` are the same attacker writing the same metadata, and a *benign* shared-repo `repository` (e.g. `github.com`) is already dropped by `isMultiTenantHost` — so splitting the two fields defends nothing under the current model. **Why C has no mechanical tripwire:** its harden-criterion fires on an *external-incident* observation, a fact about the world, not a change in this repo's code state — nothing (`candidateFields`, `multi-tenant-hosts.json`, the filter chain) changes value when it fires, so there is no RED→GREEN transition to pin; it stays KEEP-DOCUMENTED rather than being promoted to principle 30. The one mechanizable slice — a benign shared apex never leaking a shared host into Tier 1 — is *already* pinned by principle 30's paired-negative (`isOnMultiTenantList('github.com')` is caught; a single-tenant host is not), so a second test would be `#discipline-theatre`. **Harden-criterion:** if a real incident shows repository-host abuse distinct from homepage-host abuse, split the two fields and gate them independently. **Future-auditor re-check (in lieu of a tripwire):** re-verify [`multi-tenant-hosts.json`](../../packages/core/research/multi-tenant-hosts.json) *coverage* — a newly-popular shared-repo / docs-hosting apex absent from that list is the actual regression surface, not the union itself.
2. **Dep-name path-traversal (D).** `installedPkgJsonPath` (the npm `EcosystemAdapter`) does not reject `../`-segment dependency names in its `join`. Not exploitable today: an attacker-controlled `packageName` reaches that `join` (via `readInstalledMeta`) only *after* `tier1For`'s `listDirectDeps(root).has(packageName)` gate, and `Set.has` is a pure string-equality membership test — no `join` — over names read from the consumer's own trusted `package.json`. A traversal name is not a member of that set, so it is dropped before the `join` is ever reached; the operative defence is this membership gate, not a string check on the name (adding one on the CVE-class name match alone would be T16 `#pattern-matching-on-name`). **Harden-criterion:** reject `..`/`/` path segments in dependency names if a non-`package.json`-controlled dependency source is ever added to the ecosystem-adapter seam. **Tripwire:** [`ecosystem-adapter-precondition.test.ts`](../../packages/core/research/ecosystem-adapter-precondition.test.ts) makes this precondition mechanically detectable — GREEN while `npmAdapter` is the sole `EcosystemAdapter` and its dep source is the consumer `package.json`; RED the moment a second adapter or a non-`package.json` dep source lands (the two shapes that make D live).
3. **`ackFilePath` no containment (F).** `ResolveCtx.ackFilePath` is set by calling code, never sourced from plan JSON — it is not reachable from untrusted input in the current call graph (both production `validateResearchPlan` callers construct `{ root, adapter }` only, and `research-plan.schema.json` is `additionalProperties:false`, so a plan cannot smuggle the key either). **Harden-criterion:** if a plan-controlled ack-file path is ever introduced (e.g. a per-monorepo-workspace ack file selected by plan content), add path-containment validation at that point. **Tripwire:** [`ackfilepath-plan-containment.test.ts`](../../packages/core/research/ackfilepath-plan-containment.test.ts) makes this mechanically detectable — GREEN while `ackFilePath` stays confined to its `allowlist-resolver.ts` type-def + read-site and no `validateResearchPlan` ctx literal threads it (the residual anonymous-spread shape is noted in that file); RED the moment either changes.
4. **Bare-TLD ack host (round-1 B) — CODED.** `loadAckFile` now rejects a single-label ack host (e.g. `hosts: ["com"]`) with `AckFileError`, inside the same per-host loop that rejects IP-literal hosts ([`allowlist-resolver.ts`](../../packages/core/research/allowlist-resolver.ts), `loadAckFile`); paired-negative in [`allowlist-resolver.test.ts`](../../packages/core/research/allowlist-resolver.test.ts) (`hosts: ['com']` → `toThrow(AckFileError)`, with a two-label positive control). The earlier defence-in-depth still holds — an ack entry only activates via a human-reviewed, human-merged PR ([DN #2](../orchestrator-prompts/rule-research-trust-tiers/kickoff.md) human-merge boundary, cargo-vet certify precedent, [SSOT #186](../../docs/meta-factory/prior-art-evaluations.md)) — but the guard now catches a hand-edit typo (`com` for `docs.com`, which via `hostMatches` would authorize every `*.com`) at load time regardless, closing the round-1 B observation at the earliest reachable channel rather than resting on human review alone. **Prior harden-criterion (now satisfied):** reject single-label hosts in `loadAckFile` if ack files ever bypass human review — implemented ahead of that trigger for consistency with the sibling IP-literal / dup-key guards in the same loop. **Both host-derivation surfaces:** the §1.7 backward-sweep of this change found the *same* single-label gap in **Tier-1** derivation (`tier1For`'s `candidateFields` filter, which rejected IP-literal / punycode / multi-tenant but not bare TLDs — a compromised direct dep could widen its scope-locked research trust to a whole TLD via `homepage: "https://com"`); the guard is therefore applied there too, so Tier-1 package-metadata hosts and Tier-2 ack hosts reject bare TLDs consistently (paired-negative `tier1.test.ts` S2-N8). **Scope (not over-claimed):** the guard rejects *single-label* hosts only; a multi-label public suffix (`co.uk`, `github.io`) still authorizes its whole space — that is a separate property left unchanged by DN #3's exact-host / no-PSL design, not what this guard addresses.
