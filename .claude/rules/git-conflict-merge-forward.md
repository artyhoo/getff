# Git conflict merge-forward — discipline rule

<!-- channel: claude-md CLAUDE.md#merge-forward -->

> **Class:** B — enforcement mechanism is the operator-global PreToolUse guard (`~/.claude/hooks/git-safety.sh` rebase/force-push arm — fires at the moment the agent types the dangerous command) + the always-on [CLAUDE.md `Harness gates`](../../CLAUDE.md) pointer (the in-repo channel this marker declares). Class A (CI principle test) is **structurally unreachable**: the violation is an agent-session *command choice* (`git rebase` + force-push), invisible to repo CI by construction — by the time anything reaches CI the push either succeeded (plain) or was already classifier-blocked. Same out-of-repo ceiling rationale as [memory-codification.md §1](memory-codification.md). Promotion ceiling = B; §6. The «structurally unreachable» claim scopes the merge-forward **procedure** (an agent's command choice, invisible to repo CI by construction); §8's stale-base revert **hazard** is a different subject — PR-diff content lineage — which IS mechanically visible at PR time and therefore carries its own CI gate (`stale-revert-in-pr-diff`), so the Class-B ceiling stands for the procedure without extending to §8's hazard.
> **Fires:** a CONFLICTING PR (`mergeable_state: dirty`) or any `git rebase` / `git push --force*` urge on a published branch.
> **Authoritative for:** the merge-forward discipline for un-conflicting a published PR branch — §1 the rule, §2 the verified recipe, §3 why rebase+force is a dead end for agents, §4 generated-vs-semantic conflict triage, §5 anti-patterns, §6 promotion/retirement, §8 the stale-base rebuild hazard + its PR-time gate.

> **Origin:** 2026-07-21 incident, PR #1058 (worktree `night-mode-discussion-833605`). The PR turned CONFLICTING after PR #1054 moved the same generated baselines; the session rebased, then force-push was denied twice by the harness permission classifier (both direct `--force-with-lease` and pushing the rewritten history to a *new* branch), session stopped, operator had to diagnose. The rebase was never needed: merge-forward was then applied successfully — plain fast-forward push `5b784ac12..00546d4e2` un-conflicted PR #1058 with no force involved. Recurrence scale: 43 of 280 session transcripts under `~/.claude/projects/-Users-art-code-rules-as-tests-aif*/` mention `force-with-lease` / CONFLICTING (grep probe, 2026-07-21) — tens of thousands of tokens re-diagnosed per recurrence.

## §1 The rule

To fix a CONFLICTING PR, **merge the base branch INTO the PR branch and plain-push** (the push is a fast-forward of the remote PR tip, so no force is needed). **Never `git rebase` a published PR branch in an agent session**: the follow-up force-push is classifier-blocked for agents in every form, and the repo squash-merges PRs anyway, so rebase's only payoff («clean history») is collapsed to nothing at merge time.

## §2 The verified recipe (2026-07-21, PR #1058)

```text
MERGE-FORWARD (PR CONFLICTING because base moved):
1.  git fetch origin staging
2.  git checkout -b <fix-branch> origin/<pr-branch>     # from the CURRENT remote PR tip
3.  git merge origin/staging --no-edit
4.  Conflicts ONLY in generated artefacts? Check:
      git diff --name-only --diff-filter=U \
        | grep -v -e 'tests/install-sh/baselines/' -e 'plugin/hooks/'
    → empty = safe to proceed; non-empty = semantic conflict → STOP, park, operator (§4).
5.  For each conflicted file: git checkout --theirs <f> && git add <f>
    (either side is fine — the next step regenerates authoritatively)
6.  Regenerate: SNAPSHOT_MODE=capture bash tests/install-sh/snapshot.sh
    (plugin/hooks twins are regenerated by the generate-plugin-twins pre-commit hook)
7.  git add -u && git commit --no-edit
8.  Verify: SNAPSHOT_MODE=compare bash tests/install-sh/snapshot.sh → N pass / 0 fail;
    npx vitest run <affected tests>; diff both copies of any @dual-pair hook.
9.  git merge-base --is-ancestor origin/<pr-branch> HEAD   → MUST be true
10. git push origin HEAD:<pr-branch>                       # plain push, fast-forward, NO force
```

Step 9 is the safety interlock: it proves the push is a fast-forward (remote tip is an ancestor of what you push), i.e. no history was rewritten and no force flag can be needed.

**Trailer-gate interaction (range fix shipped 2026-08-08; incident 2026-08-07, PRs #1269/#1270):** step 10's plain push used to fail the pre-push `§7 Prior-art` / `§1.7` gates on *staging's own squash commits* swept in by step 3 — the hook's range was a bare `remote_sha..local_sha`, and staging squash commits routinely lack trailers (squash-trailer-loss; the server-side PR-body gate #1098 covered them at merge). Fixed at range level: the TS core scopes the gated set to `rev-list remote_sha..local_sha --not <resolved-trunk>` (`packages/core/hooks/pre-push.ts` `resolveBase` → `getCommits`), and the bash fallback additionally skips merge commits (`--no-merges` — its reduced PRESENCE check would otherwise flag the step-7 merge commit, which the TS core never flags). Consequences for this recipe:

- No `PREPUSH_UPSTREAM_REF` override is needed (that was the pre-fix workaround).
- The exclusion reads the **local** `origin/staging` tracking ref — step 1's `git fetch origin staging` is what keeps it current; do not skip it.
- Commits the branch itself introduces stay fully gated — paired-negative: `tests/hooks/prepush-merge-forward-range.test.sh` (CI: audit-self.yml `principles-meta-tests`).

## §3 Why rebase + force is a dead end for agents

- `git push --force` / `-f` — blocked by `git-safety.sh` (operator-global PreToolUse hook).
- `git push --force-with-lease` — silently denied by the harness permission classifier (verified 2026-07-21; the classifier gives no explanation, which is why sessions burned tokens diagnosing it).
- Pushing the rebased history to a **new** branch — also denied (verified 2026-07-21, same incident).
- Even if force worked: this repo squash-merges PRs, so the rebased «clean history» is collapsed into one commit anyway. Rebase buys nothing that merge-forward does not.

**Scope boundary:** the hook arm blocks rebase only for a **published** branch (`origin/<branch>` exists — force-push would be required next) and always allows `git rebase --abort`/`--quit` (the escape from an already-started rebase). Rebasing a branch *never pushed yet* stays legal — e.g. the harvest host-side `git rebase origin/staging` before first push ([egress-no-api-bypass.md §1](egress-no-api-bypass.md), [.claude/skills/harvest/SKILL.md step 4](../skills/harvest/SKILL.md)) is pre-publish and needs no force afterwards.

## §4 Conflict triage — generated vs semantic

The conflicts in this recurrence class are almost always **generated artefacts**: `tests/install-sh/baselines/*/*.fingerprint` (8 files) and/or `plugin/hooks/*` twins — any two PRs touching shipped hooks move the same files. Generated conflicts are resolved by **regeneration** (§2 steps 5-6), never by hand-merging hunks.

Anything *else* in the `--diff-filter=U` list is a **semantic conflict**: two PRs changed the same hand-authored content. That needs judgment — STOP, park the merge (`git merge --abort` or leave the fix-branch unpushed), surface to the operator with the conflicting file list.

## §5 Anti-patterns

- **`#rebase-reflex-on-conflicting-pr`** — reaching for `git rebase` because it is the muscle-memory fix for «branch behind base». For a published PR branch in an agent session it is a guaranteed dead end (§3). Counter: §2 recipe.
- **`#force-with-lease-as-safe-force`** — treating `--force-with-lease` as the «allowed» force. For agents it is equally blocked; pre-patch `git-safety.sh` advice literally recommended it, steering sessions into the wall. Counter: the hook arm points here instead.
- **`#hand-merge-generated-conflicts`** — resolving fingerprint/twin conflict hunks by hand. The files are generated; hand-merged content is authoritative-looking garbage. Counter: take either side, regenerate (§2 step 5-6), verify (step 8).

## §6 Promotion / retirement

- **Ceiling = Class B** (out-of-repo mechanism, see Class rationale). If the harness ever allows agent-committable PreToolUse wiring (`.claude/settings.json` un-deny-listed), promote the arm to an in-repo hook + same-commit self-test (`packages/core/hooks/` pattern) and re-class.
- **Strengthening trigger:** a session hits the rebase/force wall *despite* the hook arm being live → the arm's message is not landing; revise wording, count incidents.
- **Retirement:** 12 incident-free months after the hook arm ships → archive to the CLAUDE.md `Harness gates` bullet alone (peer criteria: [reviewer-discipline.md §4](reviewer-discipline.md)).

## §8 Stale-base rebuild hazard — the branch is not behind, its CONTENT is

**The incident (2026-08-08, PR #1285, repaired by PR #1298).** #1285 was *squash-rebuilt*: a fresh branch was forked from the then-current staging tip and the ORIGINAL branch's whole tree — based on an older staging — was committed over it. Every file staging had moved in between became a silent REVERSION inside the PR's own diff: `.claude/orchestrator-prompts/consumer-matrix-pnpm-flake/kickoff.md` went rev2→rev1 (discarding #1283), and `setup.d/10-skills.sh` lost its §1j block (discarding #1284 — a live consumer-facing regression).

**Why every channel missed it.** GitHub's «require branches to be up to date» is POSITIONAL, not content-based: the branch WAS up to date (merge-base was the fresh tip) and the stale content arrived as the PR's *own change* — the class is missed by construction. CI had no test over the reverted content (a docs revision + a profile-gated shipping block); a merge queue shares that blindness, because it re-runs status checks on merged trees and never compares content lineage. Human review faced 21 reverted lines inside a 2498-insertion diff — bare attention, which is not a mechanism ([attention-is-not-a-mechanism.md §1](attention-is-not-a-mechanism.md)).

**The signature and the gate.** The signature is mechanical: the PR sets a file to a blob **byte-identical to an OLDER ancestor version of that file on the base branch** — content nobody reproduces by hand by accident. Shipped as the PR-time job `stale-revert-in-pr-diff` ([.github/workflows/pr-stale-revert.yml](../../.github/workflows/pr-stale-revert.yml) → [pr-stale-revert-bin.ts](../../packages/core/hooks/checks/pr-stale-revert-bin.ts)), ADVISORY until the operator registers the context in staging branch protection. Calibration over the 150 staging squash commits back from `004864d945`: exactly 2 flags, both true positives (#1285 and its #1298 repair), zero false positives. A deliberate revert — a restoration PR like #1298 — declares `STALE-REVERT: intended — <rationale ≥20 chars>` in the PR body. The token is PR-GLOBAL by **recorded decision, not oversight**: it is expected to be rare, and the failure message names every flagged file, so a global acknowledgement still leaves an auditable record of what was acknowledged; per-file parsing waits for a real multi-file mixed-intent case.

**The fix is §2.** A branch whose base moved is un-conflicted by merging the base INTO it and re-applying the change — never by rebuilding the tree on a fresh fork.

**v1 non-goals, declared with revisit triggers:**

- **(a) Renames and deletions** — renames are not followed and deletions are not flagged. The incident class is modifications of existing files, so the scan is M-status only.
- **(b) The edited-stale-file false negative** — whole-file blob equality only catches files the PR leaves byte-identical to the stale base. A stale file the PR *also* edits produces a novel blob and is undetectable: in #1285 itself `setup.d/10-skills.sh` (stale base plus the PR's own A8 edits layered on top) would NOT flag; only the untouched `kickoff.md` does. The untouched-stale-copy shape is the majority shape of a whole-tree snapshot, which is why v1 stops here.
- **Trigger for both:** a second incident of either shape → extend the gate beyond whole-file blob equality. The SSOT entry [prior-art-evaluations.md#241](../../docs/meta-factory/prior-art-evaluations.md) carries the same trigger, plus «an upstream tool ships content-lineage revert detection → re-evaluate ADOPT».
