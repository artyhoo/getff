# Cold bottom-up design review: intent continuity

VERDICT: REVISE

Input SHA: `8048eed3bddd2c435c1809d998942284bb73fcc6`.

The proposed design can reuse the existing content-reference resolver and the structural/result vocabulary, and it correctly keeps result review distinct from a new specification-review record. The supplied PRD bytes hash to the SHA-256 recorded in the exact-content approval. The existing runtime also has a real fail-closed guard for *declared* scoped tasks and explicitly holds `contract-revision` / `product-decision` continuations. Those are usable bricks, but three binding gaps prevent the promised negative cases from being established by this design as written.

## Findings

### BLOCKER — A new/adopted task can erase its marker and enter the legacy unscoped path

Evidence: The design requires that newly authored/adopted feature work cannot claim a missing reference as an exemption (design snapshot `/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-12-intent-continuity-design@8048eed3bddd.md:125`) and proposes exact parent references on authored specs/kickoffs (`:77`). The current adapter classifies zero `intent-contract` blocks as `unscoped` (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/packages__runtime-bridge__src__resultReview@8048eed3bddd.ts:93-137`), and `enforceScope` immediately accepts that classification (`:285-293`). The older design named a prospective activation policy, exact legacy allowlist, and registration/discovery discriminator for this very distinction (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-07-idea-arch-incremental-design@8048eed3bddd.md:166-180`), but the current proposal expressly does not adopt all of those admission/index proposals as requirements (`design:13`) and supplies no replacement discriminator.

Failure-scenario: An author removes the fenced scope/reference from a newly authored kickoff (or a later launch path omits it). The bridge sees zero blocks, treats the task as ordinary legacy work, and dispatches without any spec/intent currency check. AC9's omitted-reference negative case cannot pass on this path. Before implementation approval, define the persistent adoption/legacy identity and the exact first-admission and continuation consumers that reject omission, or narrow the claimed coverage explicitly while retaining this promise as unresolved.

### MAJOR — The existing consult mailbox does not identify or address the selected document-bound responsibility

Evidence: The design says to use `class: consult`, Evidence references, and existing statuses while selecting task, architecture, or intent responsibility directly (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-12-intent-continuity-design@8048eed3bddd.md:69-85`). The supplied advisor contract defines `ASK` recipient v1 as the architecture advisor and the ask's `role` as the **sender** (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-08-10-advisor-pattern-design@8048eed3bddd.md:84-118`); its seat identity is the existing `arch.json` role (`:131-140`). The Codex transport uses one `ADVISOR.md` seed and `fork` inherits its context (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-06-advisor-codex-transport@8048eed3bddd.md:34-63`). The earlier design explicitly required a fresh `exec` product instance and a bounded recipe instead of forking that architecture seed (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-07-idea-arch-incremental-design@8048eed3bddd.md:137-141`), but no target/instantiation contract appears in the new design.

Failure-scenario: A known product question is filed as a normal consult. Existing delivery rings the architecture seed, whose inherited design conversation can influence the product answer; the ask's Evidence section may name the PRD but cannot select a fresh product-only recipient. Specify the direct routing envelope and invocation/return binding for each responsibility, including how a product ask avoids the architecture seed and how the task owner receives the answer, without inventing a mandatory relay or a global registry.

### MAJOR — The specification-review binding does not prove that its PRD was approved

Evidence: The brief contract requires an actual approval reference bound to immutable bytes, not an inference from a passing review (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/.agents__procedures__intent__references__product-brief@8048eed3bddd.md:10-19`). The proposed specification-review attempt lists feature ID and PRD/spec digests, independence, per-promise comparisons and outcome, but omits the approval reference and its validation rule (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-12-intent-continuity-design@8048eed3bddd.md:93-97`). Existing `resolveContentRef` verifies root containment and exact bytes only (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/.agents__procedures__intent__helpers__check-result-review@8048eed3bddd.mjs:85-119`); the result helper checks contract/review brief identity but has no approval-status check (`:364-372`). The current feature's approval record gives a valid specific example (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-12-intent-continuity-approval@8048eed3bddd.md:6-15`), but a generic transition cannot rely on that one record.

Failure-scenario: A candidate spec and a convincing, preserved but unapproved PRD get a `matches` comparison and matching hashes. The transition accepts it as ready for operator spec agreement, promoting author-supplied product content into apparent authority. Define how the checkpoint resolves and validates the immutable approval record against the reviewed PRD and how changed approval/PRD bytes invalidate the attempt. A digest proves identity, not authorization.

### MINOR — The claimed atomic-publication reuse is a protocol, not a supplied callable primitive

Evidence: The result-review reference requires complete attempts to appear by same-filesystem atomic rename (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/.agents__procedures__intent__references__result-review@8048eed3bddd.md:25-29`). The supplied helper states it never writes (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/.agents__procedures__intent__helpers__check-result-review@8048eed3bddd.mjs:6-16`) and exposes only read-only CLI modes (`:493-528`). The design says to reuse an “atomic attempt pattern” and defers storage details to the kickoff (`/var/folders/03/tk988ft10_92gfb989p1wrn40000gn/T/intent-bottom-review.ZKr5wa/docs__superpowers__specs__2026-10-12-intent-continuity-design@8048eed3bddd.md:95`).

Failure-scenario: A kickoff treats the validator as the publisher, or writes an in-progress review at its final path. A consumer observes a partial attempt or two authors overwrite the same attempt ID. Identify the existing stage-owner publication implementation during the implementation inventory, or specify the narrow new writer and its collision behavior. This is an evidence gap, not proof that no reusable publisher exists.

## Boundary observations

- The design's distinct specification-review type is necessary: the existing result-review shape requires observed revision, environment and implementation evidence (`check-result-review` snapshot `:220-259`), while the proposed `matches` means design preservation only (`design:93-95`). Reusing the four words does not make the old result record suitable.
- The current runtime's `within-contract` continuation is real, and its explicit hold on changed-contract/product classifications (`resultReview` snapshot `:395-425`) agrees with the proposal's later-stage requirement (`design:109`). The supplied snapshots do not include the release/start call sites, so their complete coverage cannot be verified here.
- The `/arch` source does name a written-spec transition and its existing retell checker (`ideation` snapshot `:34-52`), but no supplied snapshot shows a specification-review consumer at that transition or at plan preparation. The design presents this as an implementation delta, so the absence is not itself a shipped-behavior finding. The kickoff must locate the real consumer/effect boundaries before claiming AC2.
- The preserved approved-brief file referenced by the approval record was not supplied. I verified the supplied readable brief's SHA-256 against the approval record, but could not independently inspect the preserved copy or other live paths.

All inputs read for this review were the listed immutable snapshots only. I did not read the live checkout, chat history, handoff, or author dialogue.
