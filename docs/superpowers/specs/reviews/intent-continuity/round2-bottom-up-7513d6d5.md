## Findings

### MAJOR — The operator launch boundary is still exposed to the existing automatic dispatch paths

Evidence: The approved PRD assigns execution start to the operator (snapshot `docs__superpowers__specs__2026-10-12-intent-continuity-idea@7513d6d58eb6.md:14`, `:29`, `:55`). The revised design states that agreed specs permit autonomous plan preparation and that launch is a separate operator choice (`docs__superpowers__specs__2026-10-12-intent-continuity-design@7513d6d58eb6.md:68`, `:114`, `:125-127`). But the current `/arch` exit instructs a single-task author to put `bridge: auto` on the kickoff's first line, whose write-time hook dispatches it; it also says to try aif auto-dispatch before emitting a choice chip (`.agents__procedures__arch__references__exit-and-escalation@7513d6d58eb6.md:21-25`). The current pipeline confirms that scoped dispatch still creates a task and can run its planner before its reviewed implementation start (`.agents__procedures__pipeline__references__dispatch@7513d6d58eb6.md:21-23`). The proposal calls for making the plan/launch boundary explicit in the shared `/arch` procedure and Codex binding, but does not specify how those existing automatic paths are suppressed or made contingent on an operator launch selection. A valid specification-review attempt and admission check establish readiness, not that selection.

Failure-scenario: An agent agrees a written spec, writes the complete single-task kickoff with the currently prescribed `bridge: auto` marker, and the write-time hook dispatches a paid task before the operator chooses a launch. The AC5 check can pass at a procedural transition while the side effect has already happened. The design needs a concrete launch-authorization binding at the hook/auto-dispatch effect boundaries, including how a ready kickoff can be prepared without triggering either path.
