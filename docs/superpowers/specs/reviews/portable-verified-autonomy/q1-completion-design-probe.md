# Q1: native completion contract alternatives

> **Date:** 2026-10-26.
> **Status:** architecture proposal; not approved and not implemented.
> **Authoritative for:** this bounded comparison of completion-control choices against the already captured OpenMausBot source.
> **NOT authoritative for:** product scope, reviewer independence, installed-host behavior, a public extension API, implementation approval or feature acceptance.
> **Architecture correction:** the final A3 counterexample below supersedes any earlier inference that Q1 necessarily requires gating the same native root. Q1 may preserve the same getff task obligation across different native attempts; host-source modification is not established as necessary.

## Decision in concrete terms

**A — keep OpenMausBot unmodified, with a native recurring routine as durable task owner:** preserve the same file-backed getff obligation across distinct ordinary/goal attempts. The routine schedules subsequent attempts even when an earlier attempt says completed. This is the preferred reuse candidate for a bounded laptop trial, subject to the specific protected-obligation/retirement gap in A3 below. Ordinary assignments and room goals alone do not enforce getff acceptance, but their terminal state need not terminate the higher-level task. The exact-pin follow-up confirms that built-in routine checks are limited to calendar/mail/runs, so a ready-made deterministic getff file/command predicate must not be claimed.

**B — fallback if the task-level routine binding cannot meet the required assurance:** permit one optional native completion-contract extension while preserving the application's scheduler, assignments, engines, reviewer/workflow choices and native recovery. At the ordinary native owner's final completion boundary, require a bounded verification of the current getff acceptance evidence. An absent or rejected receipt records a durable obligation and routes the same owner into existing continuation or human-input handling. This is a host source change plus a narrow evidence binding, not a currently exposed plugin or middleware API. Its small scope is conditional on the falsifiers below; the source facts do not establish it as necessary.

For the first version, the host runs on the operator's laptop. Work continues only while the application and required engines can run. Persisted obligations can be reconciled when the application starts again; neither option promises to wake a switched-off laptop or run on an always-on server. This follows the host timer at index:9915–9935 and runtime startup at runtime:77–120. The host may create/manage its sessions, and its bots may invoke the existing AIF plan/work/review procedures; neither option replaces that workflow.

## A — what the unmodified application can actually do

The owner can send work through native `coordinate_bots`, obtain assignment IDs, yield, receive results in its resumed turn, call the existing AIF/getff procedures, send concrete `rework:true`, and repeat. The relevant native schema and return instructions are index:14764–14780 and :14707–14712; deduplication/rework behavior is coordinator:192–219. Actual outstanding or unseen awaited children hold the owner in `waiting` (runtime:478–490). Thus an owner that has already dispatched an awaited review cannot finish while that review is outstanding, even if its model turn ends.

After those results are consumed, successful completion is unconditional in the inspected branch (runtime:492–494; coordinator:488–497). `done_when` is a stored string, not a verified predicate (types:91–94; coordinator:208–209). A rejection returned by the reviewer does not itself force rework. Adding a permanent “sentinel” child only moves the same trust problem to that child's behavior and consumes existing depth/turn budgets; the captures do not expose an externally settled acceptance child. That workaround is not proposed as a mechanism.

The existing host Claude Stop event returns OK without a getff check (index:5798), and the captured Codex adapter does not advertise that host hook path (codex:1798–1816 versus index:8657–8659). Project Claude hooks are a possible separate experiment, but their getff firing, veto semantics, configuration merge behavior, restart behavior and cross-engine equivalence remain unproved (claude:1074–1078,1203–1210). They cannot be sold as option A's established completion mechanism.

**Tradeoff:** no host patch or upstream maintenance; useful native delegation remains usable. However, when the owner prematurely succeeds with no outstanding children, getff must remain unaccepted and someone or another proven owner mechanism must resume work. There is no demonstrated durable automatic acceptance-driven resumption in this source path. Choosing A means accepting that limit for the slice, not silently asserting full Q1 satisfaction.

### A2 — fair reuse countercheck: native room goal mode

The captured application has a real goal mode, not just a suggestive `goalRunId` field:

- `startGroupTurn` accepts `channelMode:chat|goal` (index:11362–11369), validates a requested lead (:11389–11393), and selects the lead for goal mode (:11470–11473). A goal card/run is initialized and `runGroupGoalOperation` is invoked (:11531–11562,11577–11578). This proves an internal application path, not the exact public/UI submission API.
- The goal loop repeatedly runs the coordinator, parses its decision, runs a selected worker and returns to the coordinator (index:11173–11189,11234–11291,11330–11348). It handles unavailable/busy/parked members, retries certain transient step failures once, limits repeated assignments and can ask the lead to reassign (index:11050–11125,11265–11275,11306–11328). A worker merely finishing does not itself finish this outer goal.
- On a parsed non-continue decision, it immediately calls `finishGroupGoalRun` with that status/detail (index:11234–11246). That function marks finished and writes status into the goal card/routine completion (:4412–4435). No explicit current getff receipt/candidate check is visible at that transition. If the lead provides no valid decision the loop blocks, rather than blindly treating arbitrary text as success (:11234–11242).
- At the turn limit, it records `limit-reached` and explicitly asks to send the goal again (:11342–11348). A goal step interrupted across restart refuses rerun when its goal is no longer live (:4053–4055); `goalRunLive` consults current in-memory operations (:10034–10036). Startup reconciles persisted goal records with routine outcomes, including failure after restart (:9279–9301); that is not visible evidence of resuming the goal's control loop.

This is a meaningful reuse candidate: existing AIF/getff work and review could be assigned inside that native loop. It may reduce procedural coordination work relative to ordinary assignments. It must not be omitted from the choice merely because the earlier ordinary-root finding was negative.

**Direct owners resolved at the same pin:** the [goal helper](q1-source-addendum/server__group-goal-run.ts):53–79 only parses the last complete control envelope and accepts `completed` with nonempty bounded `detail`; no candidate, reviewer or receipt is required. Its instructions tell the coordinator to decide from the conversation and avoid claiming completion before a deliverable is present (:124–128); that is model guidance, not evidence validation. [Application store](q1-source-addendum/server__store.ts):965–1006 reconciles working goal cards to a supplied terminal/parked result or failed fallback; it does not restart the goal loop. [Routines](q1-source-addendum/server__routines.ts):1320–1348 accepts the provided goal status and records completed without an acceptance check. Its `rejectResult` can change a completed run to failed (:1295–1299), but does not itself enqueue rework. Startup only processes running/waiting runs (:380–398), so an already completed false-success is outside that recovery loop.

One narrower restart uncertainty remains: routines imports `requeueOnce`/`recoverRun` from `server/routine-recovery.ts` (:24–26), outside the authorized three-file follow-up. Some interrupted scheduled runs may requeue through that helper; do not claim all scheduled room goals fail after restart. This does not cure false success: completed runs are excluded at the caller, and the terminal decision requires no getff evidence. The shared goal status type was not fetched because the decisive parser and completion bodies already resolve the acceptance question.

**Disposition:** A2 is a reusable goal-attempt coordinator, but cannot alone serve as the trusted getff acceptance authority. **Correction to the initial inference:** this does not establish a need for a completion-contract host patch, because A3 can retain task ownership across completed goal attempts. If architecture nevertheless needs to gate the native goal's terminal decision, the local source change point would be before index:11244–11246 and would require separate goal-loop persistence/re-entry proof. Do not apply the ordinary-root B below to individual goal steps and claim to have gated the outer goal.

The contract must be bound before the first owner execution can complete. ## Required durable binding — more than a continuation note

The proposed contract record needs the following semantics; these are design requirements, not existing field names or a promised API:

1. **Authority and target:** immutable contract ID/hash and version; the host root/owner identity; getff task identity and authorized scope; the authoritative current-candidate reference; required acceptance/delivery stage. A candidate may advance during repair, but an old candidate's passing receipt cannot authorize the new candidate. Bind receipt to the candidate and scope actually checked, not a mutable file path alone.
2. **Checker identity:** pinned checker implementation/configuration and protocol version, resolved through host-controlled opt-in configuration. The task text and worker must not be able to replace the checker or declare an arbitrary command trusted. The checker validates evidence provenance/authority as well as content; agent-authored “pass” JSON is not sufficient. Exact reuse of existing getff validation remains an implementation prerequisite.
3. **Attempt and decision:** a monotonic completion-attempt identity, candidate digest checked, receipt identity/hash, decision and reason, and the bound checker version. `Assignment.version:1` in types:147 is not an existing optimistic concurrency counter; do not reuse it as one. A late result is accepted only for the still-current live attempt, root and candidate.
4. **Continuation obligation:** durable pending/repair/check-unavailable/decision-needed disposition with bounded retry history; explicit accepted or cancelled retirement. Persist this independently of `continuation.note`, because that note is cleared at dispatch (types:134–136; runtime:384–385). A restart during the next execution must still know that the root is contracted and unaccepted.
5. **Atomic decisions:** pending disposition and queue/park transition commit together; a valid receipt decision and terminal completed transition commit together. Duplicate finish events, restarts or late checker results must not produce a completion without the bound evidence or enqueue extra independent roots.

The smallest viable checker is a bounded, read-only verification of already-produced local evidence. It does not perform model calls, repairs, deployment or network publication in the finalizer. Pure local validation fits the existing synchronous `finishTurn`/store transition most closely. Do not run an arbitrary shell command, await network I/O or hold a database transaction while waiting for an LLM in that path. If existing acceptance verification requires asynchronous work, the minimal design changes: a durable pending-check record and native tick-driven reconciliation are needed before settlement. That is an explicit scope fork, not an invisible “callback” addition. No claim is made that the current store exposes such a record type.

## Tradeoffs and falsifiers of a small extension

| Choice | Benefit | Cost / unresolved obligation |
| --- | --- | --- |
| A, strict unmodified host | Reuse native assignment return or the existing room goal lead/worker loop; no host fork. | Goal helper accepts completed with only model detail; false completed goals are outside startup recovery. Product acceptance may remain safely false while progress stops. |
| A3, unmodified recurring routine above attempts | Existing durable schedule can return to the same pending getff task after an attempt completes; no native root must be resurrected. | Built-in checks cannot express arbitrary getff file/command validation. Current-evidence invocation and protected routine retirement/control require the specific feasibility proof below. |
| B, optional native contract | Engine-neutral completion enforcement at the common native root boundary; reuses current queue, restart, input and stop mechanics; no separate scheduler. | Host source maintenance/upstream work; persisted schema and success-display changes; exact getff checker binding and adverse-cut proof. Reviewer isolation is still a separate unresolved contract. |

Treat B as viable only while all of the following remain true. These are stopping tests, not claims already verified:

- Both direct and resumed native completions pass one check; a wrong/stale/forged receipt cannot reach completed. A bypassing success route or user-visible “accepted” surface that cannot be narrowly corrected falsifies the proposed boundary.
- A local read-only checker can validate the actual existing getff acceptance evidence without reimplementing its semantics or launching a replacement workflow. A required asynchronous remote policy engine or parallel scheduler falsifies the synchronous minimum and requires a new explicit scope choice.
- Pending obligations, checker identity and candidate/version binding survive crashes before/after queue commit, dispatch and final settlement; old/duplicate results cannot advance current work. If the existing store cannot support the atomic boundary without a larger redesign, the “small extension” estimate is false.
- Existing stop, input park, effect fence, one-rerun protection and loop budgets still win. If convergence depends on disabling them, B is not acceptable as proposed.
- A laptop restart can recover when the app is started again, without an always-on server. If the requirement actually demands progress while the laptop is off, neither A nor this B meets that changed requirement.
- The actual getff reviewer can meet its independent-input contract. This completion extension cannot turn contaminated review evidence into an independent verdict; Q1 success does not close that separate question.

The corrected decision is concrete: test A3's existing native routine as the durable task owner before choosing host work. Keep A1/A2 as its execution routes; keep B as a reviewed fallback if A3 cannot protect the required obligation and control boundaries. This document authorizes neither setup nor implementation and does not weaken the approved product promises by implication.

## A3 counterexample — a native routine owns the task across attempts

**Disposition: retain as a concrete reuse alternative; mandatory host modification is not established.** The previous A/B framing conflated the continuing getff task obligation with one native root's lifetime. If the product requires the same getff task, rather than the same native root, that restriction was narrower than the product requirement. An existing recurring OpenMaus routine can survive an individual ordinary/goal attempt's completed status and schedule another attempt against the same file-backed getff obligation. The premature-completion counterexample remains true for the attempt but does not, by itself, prove loss of the higher-level task owner.

This is reuse of the host's existing routine scheduler, not a new scheduler or a permanent sentinel child. The source supports its scheduling foundation:

**Proposed reuse binding, not an existing configured installation:** one ordinary recurring native routine refers to a stable getff task/obligation identity and its authorized acceptance authority. Every attempt first re-reads current task state; if pending, it resumes the existing plan/work/review flow and reconciles prior effects; if accepted, it performs no further work. Native attempt IDs remain execution evidence only. Each attempt may have a new root or goal-run ID. This avoids requiring reopening a terminal native root. A deliberately wrong completed attempt should leave getff pending and the routine enabled, so a later scheduled/startup attempt has another opportunity to repair it.

There is also a **real pre-run checks seam**: `RoutineChecks.check` returns an optional run prompt/key, trouble and wakeAt; it has a settled-result callback (routines:202–212). The routine manager checks before creating work, persists check state, does not create a scheduled AI run when nothing is needed, retries check trouble on later checks, and rechecks enabled state after an asynchronous result (routines:1195–1237). Index wires this to `proactive.checks` (index:9153–9154). This could be a closer fit for a file-backed pending obligation than unconditional model polling, **if** an existing supported check type can actually express and protect that predicate.

The two directly referenced check owners have now been fetched at the same immutable pin, with [separate receipts](q1-source-addendum/routine-check-fetch-receipts.json). [Shared routine types](q1-source-addendum/shared__routines.ts):65–68 define the closed built-in check union `calendar | mail | runs`. The comments specify calendar events, new mail and other routines' finished runs; there is no command/local-file/custom-predicate alternative in the exposed type. [Proactive wiring](q1-source-addendum/server__host__proactive.ts):131–147 constructs those checks, wraps them for personal/team/brief ownership and forwards settled results; its default watch uses the same three checks (:217–220). The concrete check engine is imported from `server/host/routine-checks.ts` (:30), which was deliberately not fetched. Its hidden internals cannot be advertised as a supported arbitrary getff command field absent from this captured public shape.

**Available permissions do not close the protection gap by themselves.** Shared routine types:70–72 provide only the special `read-and-draft` access value; omission uses the bot's own level. That mode is documented to allow Gmail/Calendar reads and reply drafts while refusing every other tool, so it is not an available shell/coding/getff-checker mode. Proactive wiring instantiates the fence (:148–153) and advertises the relevant fully fenced engine set as only `claudeAgent` (:34–35); it does not establish Codex equivalence or a coding-capable “cannot change my routine” permission profile. Routine create/update/delete authorization remains delegated to the uncaptured `server/routine-requests.ts` and route/fence implementations (index:454,9356–9371). No further dependencies were fetched. Therefore worker permission to modify/disable the actual routine is **unknown**, not assumed either allowed or denied.

**Concrete supported scheduling setup to take to a future trial:** an ordinary recurring routine without `checks`/brief/read-and-draft mode, targeting a bot or room goal, with a stable getff task reference in its prompt, an appropriate non-ended schedule, and optionally `runOnStartup:true`. Each scheduled attempt can invoke the existing getff evidence check and AIF workflow through its normal authorized tools. This is configuration-level use of captured fields and dispatch paths, not proof that prompt compliance supplies deterministic task acceptance. The check must still validate authoritative evidence and the routine must not be prematurely retired. Using `checks:["runs"]` is not equivalent: a finished-run event is not a current-candidate accepted-result predicate.

**Laptop startup entry is concrete:** captured index:16492 calls `routines.start()` through `moveFreeze.hold`; RoutineManager.start queues eligible startup runs then ticks and installs its existing timer (routines:951–956,970–1004). An already enabled recurring definition with the startup flag can therefore produce a new attempt after a previous completed one, without resurrecting that completed root. The definition must remain enabled, not expired, and subject to freeze/target/active-run checks. This preserves laptop-only deployment; it neither wakes a powered-off machine nor creates an always-on server.

### Scheduled re-evaluation is supported; protected termination is not yet proved

The manager mechanically schedules future enabled occurrences regardless of a prior attempt's completed status. It does not itself verify that every attempt reads the real getff obligation, that the accepted marker has trusted provenance, or that the model cannot disable/delete/change the routine while the obligation is pending. In the inspected update/remove bodies there is no getff-specific acceptance precondition. Their authorization is a separate layer, so this is not a claim that arbitrary callers can disable routines.

Two boundaries must therefore be proven for A3 before claiming Q1:

1. **Durable admission and recheck:** the native routine retains the same getff task reference across attempts/restart; it stays enabled while pending unless an authorized human pauses/cancels; any deterministic check uses current trusted acceptance evidence and fails closed. If only prompt-level re-reading is available, state that weaker assurance explicitly. A routine that merely starts more model turns is not proof of completing the obligation.
2. **Protected retirement and control:** the attempted worker cannot declare the obligation accepted or retire its owner by model assertion. Native controls must distinguish an authorized pause/cancel from a purported task completion. A supported acceptance-bound stop predicate or demonstrably sufficient capability restriction may provide this boundary; neither is established by the captured manager interface. Indefinite idle recurring model runs would also carry avoidable quota/effort costs and are not automatically the desired closure behavior.
