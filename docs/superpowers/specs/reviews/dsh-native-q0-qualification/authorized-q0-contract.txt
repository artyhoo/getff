## §1 Objective, satellite boundary and constraints

Qualify the complete DSH application as a separate getff satellite, directly coordinating and executing the selected task path without AIF. Keep portable getff intent, workflow prerequisites, project conventions and independent current-result acceptance. The intended simplification removes unnecessary lifecycle boundaries; no superiority, cost saving or completed autonomy is claimed before measurement.

DSH and its required Harness live in a separate checkout/profile/state directory. getff owns only the binding, portable procedures/evidence and installer dependency closure. Prefer upstream's supported top-level installation/setup after detect-first; do not vendor the application into `packages/core` or reproduce its installer. The [companion install rule](../../../.agents/rules/companion-install-principle.md) governs eventual consumer installation: no consumer install-command version pin or silent paid-API default. For the isolated trial, record and reproduce exact checked-out revisions/dependency resolutions; an upstream change is a distinct observed version, never silently relabeled as the frozen research target.

Global constraints:

- PA1–PA9 and PC1–PC7 retain the meanings in specification §§8–9; staged proofs do not waive them.
- The candidate task path has no AIF runtime/task/claim or automatic AIF fallback. Existing unrelated AIF users and active work remain under their current owners.
- DSH owns the outer obligation; one worker owns each candidate/correction. Reviewers are independent read-only checkpoints. No additional scheduler, global task registry, model router or memory platform.
- Use eligible existing subscriptions or free required operations for coordinator, workers, reviewers, memory and hosting. Unknown account/cost is a hold; required new payment rejects this candidate under present constraints.
- Preserve normal authentication, policies, permissions, hooks and actual stage prerequisites. No fake AIF IDs, bypass flags, disabled gates or fabricated approval/review records.
- `ready`, native ticket completion and PR closure do not prove current product acceptance. Audit completion **and continuation** across all terminal paths.
- Production cutover, taking over active tasks, paid model calls, changing PC access/power, live messaging and merge/deploy are outside this drafting request. Later scoped execution inherits only its actual grants.
- All internal artifacts are English; operator-facing summaries are Russian. Preserve the original research corpus and its frozen hashes.

## §3 Q0 task package

Q0 is a bounded compatibility investigation using a separate checkout/profile and disposable fixtures. It may install/build isolated upstream dependencies after its later execution grant permits setup, but does not modify product integration source, enroll production channels or start paid models. Findings produce a plan, not an improvised lifecycle rewrite.

### Task A — bind destination and reproduce source/build closure

- [ ] Record actual execution host, OS, repository root, branch/HEAD, relevant tool versions, target PC identity if legitimately available, and isolated checkout/profile/state paths. Never copy credentials or whole private configuration into a report.
- [ ] Detect existing DSH/Harness before installation. Read actual upstream `SETUP.md`, `docs/006-deployment.md`, package/lock manifests and supported setup entry points. Inspect lifecycle scripts before running dependency installation. Use a disposable account/profile and synthetic repository/destination data for Q0.
- [ ] Materialize complete DSH source as the satellite checkout, retain upstream notices, and record actual revision, lockfile and resolved host dependencies. Check the frozen matching revision first; independently identify any newer upstream version considered.
- [ ] Run the upstream-declared checks (`pnpm check` for the captured DSH) from the real satellite checkout after prerequisites resolve; retain complete command, cwd, exit status and sanitized stdout/stderr. A missing dependency is a concrete build prerequisite, not a skipped passing check. Record exact Harness setup/start diagnostics independently of DSH source tests.
- [ ] Preserve outcomes in `environment.json`, `sources.json` and `raw/`; label SOURCE, TEST, RUNTIME, REPORTED and UNKNOWN per claim. A cloud build says nothing about actual PC installation until repeated there.

### Task B — qualify direct worker capabilities and account route

- [ ] Inspect exact-version provider registration/configuration and effective managed-worker tools **after** restrictions. Distinguish global provider existence, worker visibility and successful invocation.
- [ ] With synthetic/fake providers and no paid model calls, exercise the real managed-worker path where feasible: submission, result callback, error, cancellation and result after disconnect. Preserve ticket/assignment/owner/result identities and actual tool/input inventories. A standalone provider fixture is not managed-worker activation.
- [ ] Inspect the legitimate account route using supported non-secret status/first-party account information. Cover the DSH coordinator model separately from Codex/Claude/GLM children. Verify normal local configuration and authentication are preserved. Without sufficient evidence, mark eligibility UNKNOWN and gate Q2; do not log in, extract credentials or silently switch to a paid provider.
- [ ] Enumerate actual reviewer inputs: repository/global instructions, prompt sections, memory/MCP/plugins and native-provider configuration. Use synthetic author-rationale and cross-project sentinels when an actual permitted review-profile fixture is available. A no-history switch alone proves no isolation.
- [ ] Return `providers-and-context.md` with each of exposure, lifecycle, eligibility and reviewer isolation classified separately. A live semantic/account proof outside the Q0 grant remains an explicit later prerequisite.

### Task C — map replacement duties and completion/recovery paths

- [ ] Enumerate the complete AIF-dependent duty population before judging replacement: admission and cross-route claim, applicable plan review, workspace/execution, technical review/rework, observation/result identity, correction custody, independent product acceptance and permitted delivery.
- [ ] For each duty identify the existing getff mechanism, concrete DSH/native replacement seam, required delta, tests, consumer assets and unresolved prerequisite. No hidden AIF fallback or synthetic task IDs.
- [ ] Enumerate terminal/effect paths before proposing a ready gate: worker ready/dropped, followed PR closed/merged, explicit stop, restart, late result, quota/provider hold and uncertain remote effect. Explain both how false acceptance is refused and how the next permitted action resumes under the same durable obligation.
- [ ] Demonstrate current-revision/authority validation using existing helpers on disposable valid/invalid records. Synthetic review records must be clearly labeled test fixtures and never published as real independent judgments. Reuse P01/P04 only for their actual scope.
- [ ] Produce `replacement-map.csv` and `terminal-paths.csv`, with file/function anchors, observed level, missing behavior and the smallest proposed change. Do not edit DSH engine/scheduler/executor during Q0.

### Task D — concrete integration decision and Q1 handoff

- [ ] Write `Q0-REPORT.md` distinguishing observed build/tool behavior, eligibility limits, duty coverage, host-patch footprint, upstream upgrade cost and remaining PC/consumer/second-host proofs. Compare with the strongest OpenMaus recurring-obligation/native-return route, not only a finite observer.
- [ ] Choose a factual disposition: `QUALIFIED_FOR_Q1`, `HOLD_PREREQUISITE`, or `REJECT_PRESENT_CONSTRAINTS`. This is not production adoption. A paid-required route or a plan to recreate the host lifecycle violates the present boundary; identify the actual cause and bounded alternative rather than silently expanding scope.
- [ ] If Q1 is feasible, prepare a scoped implementation plan with actual files/interfaces/tests, including report and all other completion paths. Retain independent getff review, single custody, current authority/candidate checks and native recovery; use existing mechanisms first. Do not invent module/API names before identifying the actual supported seam.
- [ ] Run a fresh artifact-only review of the Q0 evidence and proposed delta before Q1 is offered. Capture raw commands and exact source bindings; fix concrete evidence defects within Q0. A material product/architecture fork returns with alternatives and consequences.

## §4 Output contract and evidence ownership

Use the existing bound stage artifact root on the executing host. Portable repository records belong under `docs/superpowers/research/dsh-getff-native-autonomy/<actual-run-date>/q0/`; these output paths describe future files, not files already present. Keep account identifiers, host paths and secret-bearing traces consumer-local; export only sanitized evidence and reproducible commands.

Required outputs:

| Artifact | Contract |
| --- | --- |
| `Q0-REPORT.md` | Scope, disposition, actual environment/revisions, findings, remaining prerequisites, bounded patch and maintenance proposal; no adoption claim. |
| `environment.json` | Observed host/tool/profile/state identity and command receipts; distinguish local observations from reported PC state. |
| `sources.json` | Source path/revision, capture origin, SHA256 and exact claim binding. |
| `providers-and-context.md` | Per-route exposure/invocation/callback/cancel/isolation/eligibility evidence; coordinator costs included. |
| `replacement-map.csv` | Duty, existing mechanism, candidate seam, source/evidence, delta, test, consumer surface, unresolved prerequisite. |
| `terminal-paths.csv` | Entry path, current transition, acceptance guard, continuing owner/wake, late/duplicate behavior, required adverse test. |
| `raw/` | Sanitized commands, cwd, exit codes, stdout/stderr and fake-input fixtures; failures retained. |
| `output-manifest.json` | Exact bytes/digests for returned artifacts, excluding itself; names absent required artifacts explicitly. |
| `Q1-PLAN.md` when feasible | Concrete bounded plan over verified source/API seams; includes negatives, recovery and upgrade regressions. Otherwise give a precise prerequisite/action owner. |

Every observation binds to the actually tested system and version. Relevance to several architecture options is not execution on those options. No semantic verdict is inferred from receipt/hash validation. Only the read-only independent reviewer authors its judgment; the coding owner remains accountable for repairs.

## §5 Acceptance and review focus

Q0 can be accepted only when the output population is complete, source bindings resolve, commands and failures are preserved, direct-worker seams and all AIF replacement duties are accounted for, terminal/continuation paths are enumerated and the smallest integration delta is buildable or explicitly held. A missing eligible live account may hold Q2 while bounded fake-host/build work still proceeds; it must never become a claimed account pass or an automatic rejection without evidence.

Five priority failure classes and their owning task:

1. Provider exists globally but is removed by worker restrictions — Task B tests the effective worker boundary.
2. Coordinator needs a paid API although children use subscriptions — Task B records both routes and gates live enrollment.
3. Native ready/PR close ends work before independent acceptance or leaves no continuing owner — Task C enumerates all terminal paths; Task D requires executable guard and recovery tests in Q1.
4. Timeout/late result or duplicate intake creates a second coding owner — Task C maps actual identity/reconciliation; Q1 includes interrupted and duplicate paths.
5. Fresh reviewer inherits author/project-B context — Task B records effective inputs/sentinels; absent real profile proof remains a Q1/Q2 hold rather than a clean isolation claim.

Q1/Q2 completion also requires wrong-product, stale-evidence, real finding/repair/recheck, effective pause/cancel, lost-response reconciliation and useful-cycle evidence from the spec. Q3 and Q4 stay explicitly open. Count setup, maintenance, recovery, no-op model calls and actual operator relays; do not claim a cheaper factory from an unmeasured architectural diagram.
