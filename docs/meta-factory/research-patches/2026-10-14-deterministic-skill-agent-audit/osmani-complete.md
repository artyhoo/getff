## Human approval, force-discipline and authority costs

- Interview: single question each round, rejects delegated “whatever you think” and conversational “sounds good/sure”, demands immediate terminal turn on explicit confirmation. This can be appropriate for unclear product intent, but adds friction when the operator already delegated exact-brief approval. Local operator delegation binds immutable content and does not authorize spending, security changes or main merge.
- Spec: human review at capability map/spec/plan/task stages, spec must stop its turn and wait for later-turn approval. Local /intent and /arch already own product boundaries and content-bound review (G3/G4). Importing the literal next-turn stop would duplicate an authority gate under the user’s current delegation.
- Build auto is a useful exception: one plan approval then all tasks, preserving tests/commits, but pauses on ambiguity/high-risk changes. It is not unrestricted autonomous operation and does not transfer main/deploy authority.
- Doubt: fresh review is bounded at three cycles; cross-model option is mandatory every interactive cycle; external CLI every invocation gets exact syntax and explicit authorization. That is repeated time/cost overhead even when an existing configured local reviewer would suffice. The source states non-interactive runs must skip unauthorized external CLI.
- Browser/security: browser-content URLs and JS mutations require confirmation; security “ask first” covers auth/integrations/CORS/uploads/rate limits/data classes. These are upstream policies to compare with existing authorized scope, not new instructions for this research session.
- Force rhetoric: “skills are workflows, not suggestions”, 1% matching, absolute every-change review and rationalization rebuttals improve prompt salience but remain instructions. getff’s G2 explicitly separates judgment injection from deterministic gate. Do not advertise these prose obligations as unbypassable runtime enforcement.
- Verification repetition tension: incremental/TDD say do not rerun an unchanged successful command; local verification-before-completion requires a fresh run in the claiming message. The right freshness boundary depends on whether code/environment/input changed and existing evidence binding, not blind ritual.
