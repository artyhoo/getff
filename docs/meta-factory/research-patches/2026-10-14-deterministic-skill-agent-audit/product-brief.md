# Deterministic core with benefit-led automation

> **Authoritative for:** the product promise of this feature once bound by the adjacent exact-content approval record.
> **NOT authoritative for:** the framework's overall goal, solution architecture, implementation authorization, or a claim that any new behavior is already delivered.

## Product experience

Framework maintainers prepare a common, ready-made core of principles, skills, agents, hooks and supporting mechanisms. Its users should receive dependable execution of formal operations without asking a model to reconstruct the same procedure on each invocation. This is especially valuable when a less capable model performs the surrounding task: established mechanical obligations should not depend on its memory, prose interpretation or clerical accuracy.

The model should normally see the purpose, applicable constraints, invocation contract, unresolved judgment and useful result. Detailed procedural implementation should remain available for diagnosis without occupying routine context. Known formal work should execute through the relevant entry point or trigger, with an honest distinction between completed, failed and unavailable work.

The investment begins in the shared core. Its mechanisms and tests deserve thorough engineering because improvements and defects propagate across many uses. The long-term direction is to mechanize deterministic work; the practical question is which operations deliver the most benefit first. Select bounded, valuable increments rather than withholding useful results until every possible abstraction and automation exists.

Prioritize operations where relatively little effort produces a large useful result. Frequency, repeated model effort, clerical failures, reuse and implementation/maintenance cost should inform that judgment. No ratio, quota, percentage or numeric prioritization rule is implied. Each increment should have a demonstrable outcome and a stopping boundary, so the initiative produces usable improvements rather than endless construction. This brief establishes no separate lightweight installation mode or relaxed quality policy for small projects.

Begin by applying this approach to the framework project itself. Consumer delivery remains a separate acceptance boundary: success in the contributor repository must not be presented as proof that every installed project has acquired the same behavior.

## Meaning and scope

- **Ready-made core:** maintained, reusable framework capabilities delivered through supported installation profiles/channels. It includes principles, skills, agents, hooks and supporting mechanisms. This is a product boundary, not a declaration that every audited operator artifact ships to every consumer.
- **Project-generated artifacts:** rules, tests and configuration tailored after installation to a project's stack and needs. They may use substantial reusable core machinery without requiring equally substantial new bespoke machinery.
- **Mechanical work:** an operation with a sufficiently specified contract for execution and verification without a new semantic decision. A mechanically executed remote query can fail or return incomplete evidence; determinism does not imply network reliability or semantic completeness.
- **Simplicity:** the simplest sufficient structure, assessed across callers, maintenance, agent context, verification and operation. Repeated genuine decisions should have one owner; superficial similarity alone does not justify abstraction.
- **Benefit-led prioritization:** choose the next deterministic responsibilities by expected and then observed value, with a bounded scope and completion criterion. The shared core is the first investment area; no per-project installation or assurance policy is introduced here.

The coverage objective is all deterministic/mechanical responsibilities in the selected ready-made core population. Delivery is incremental: a bounded stage can complete while the broader coverage inventory still has residual work. Keep remaining responsibilities and genuine judgment boundaries visible without making complete automation of the universe a prerequisite for delivering a useful stage. This does not require one script per instruction or a new universal workflow engine.

## Scenarios, failure cases and permitted deferrals

### DC-P1 — execute the known contract

Scenario: a core skill requires an inventory and a structured report. A reusable mechanism performs the formal acquisition/validation/publication steps; the agent decides what the findings mean. Given equivalent valid inputs, different capable callers obtain the same formal checks and result semantics. The trigger may be an explicit skill entry or a relevant host event; mere reminder text is not evidence of execution.

Failure: the model must remember a long shell recipe; it can silently omit a required formal step; or a script invents a semantic verdict from a syntactic check. A failed acquisition reported as a clean empty inventory also fails this promise.

Permitted deferral: individual capability families and hosts may be phased with explicit residual coverage. Not permitted: claiming the core objective complete while known in-scope mechanical responsibilities remain silently prose-only.

### DC-P2 — reserve context for useful reasoning

Scenario: the agent receives a compact invocation/result contract and the evidence needed for its decision. Full logs and implementation are accessible when a failure requires investigation, without being loaded on every routine run.

Failure: a shorter skill eagerly loads equivalent or larger references/logs, hides an essential precondition, or leaves the caller unable to diagnose a failed mechanism.

Permitted deferral: universal caching or automatic context management. Not permitted: removing information necessary for correct use or reporting byte reduction as measured token savings.

### DC-P3 — trust the shared machinery for reasons

Scenario: a core validator accepts a correct result, rejects a relevant bad result, and its assurance detects an implementation that returns success without checking. Expected outcomes come from the intended contract rather than being recreated by the same production logic. Evidence covers the actual invocation path as well as the helper where relevant.

Failure: assertions check only file existence or output shape while wrong behavior passes; a missing/disabled check is reported as successful; a shared diagnostic from another rule supplies a false success.

Permitted deferral: exhaustive platform coverage and a particular test technology. Not permitted: treating a tautological green suite or an uninvoked check as assurance of the advertised behavior.

### DC-P4 — deliver the most useful automation first

Scenario: several formal operations are candidates. One repeatedly consumes model context and causes clerical errors across core skills; another is rare and costly to automate. Select a bounded increment with explicit expected benefit, confirm the actual result and use that evidence to choose the next increment. A completed increment is usable before the full inventory is converted.

The long-term goal remains mechanization of deterministic work. Prioritizing or deferring a lower-value operation does not reclassify it as judgment or pretend it is already automated.

Failure: the first usable result waits on a universal engine, more framework layers become the success metric, scope expands without closure, or an illustrative analogy becomes a numerical requirement. A convenient sample presented as full coverage also fails.

Permitted deferral: lower-priority families and exact numerical optimization targets, with residual work visible. Not permitted: abandoning prioritization and bounded completion or misrepresenting a stage as full automation coverage.

### DC-P5 — reduce total complexity

Scenario: common report mechanics are shared while distinct reviewers retain their judgments. A useful boundary removes repeated decisions from callers. Existing owners carry the named simplicity criterion.

Failure: fewer lines in a skill introduce extra registries, state synchronization, pass-through layers or duplicated caller logic; semantic differences are erased to force all operations into one pattern.

Permitted deferral: final naming and exact wording of the simplicity criterion. Not permitted: measuring simplicity by script count, line count or a universal numeric threshold alone.

### DC-P6 — prove locally, then establish delivery

Scenario: a bounded core family is exercised on this repository through real callers. A subsequent delivery claim is supported for the relevant install profile and activation path. Operator-only procedures remain identified as such.

Failure: a helper's presence or local unit test is presented as proof that an installed consumer actually runs it, or all operator capabilities are silently added to the consumer default.

Permitted deferral: consumer breadth and later capability families. Not permitted: collapsing source, delivery and activation into one unsupported claim.

### DC-P7 — show benefit without moving the goalposts

Scenario: comparable tasks capture relevant model input, tool-output volume, repeated calls, time, clerical failures and repair work. Where model capability is compared, the same formal contract and acceptance criteria apply. Less capable models benefit specifically where mechanisms take over formal work; semantic reasoning remains evaluated separately.

Failure: corpus size is reported as token savings, a stronger model compensates for missing mechanisms, or faster runs omit necessary checks. No guarantee that arbitrary models can perform arbitrary semantic work follows from this feature.

Permitted deferral: a universal savings percentage, calendar estimate, all-model benchmarking and paid evaluation infrastructure. Not permitted: claiming an observed reliability or efficiency improvement without evidence, or weakening acceptance to manufacture one.

## Rejected interpretations

- This feature defines a new lightweight installation mode or a separate relaxed quality regime for small projects.
- Every prose instruction deserves a separate script, or any repeated text deserves a generic abstraction.
- Every operator capability is necessarily default consumer payload.
- Smaller models become generally correct because some operations are mechanized.
- Fewer tokens, fewer lines or a successful process exit alone establish product success.
- Prioritization means claiming deferred deterministic work is already automated, or granting permission to bypass existing required checks.
- Product-brief approval grants implementation, integration, installation, publication or main-merge authority.
- Original external sources and independent ports are interchangeable evidence.
