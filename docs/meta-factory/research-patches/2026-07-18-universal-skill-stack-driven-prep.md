# Universal skill, stack-driven: research prep

## §0. Why this doc exists

The operator raised an architectural idea and asked to validate it before any work: *"в каждом проекте создаю скилы под каждую версию каждого инструмента заново — а разве нельзя абстрагировать и создать общий универсальный каркас … а упираться он уже будет под изменчивую и сгенерированную под каждый стек заново документацию?"* The operator explicitly wanted **discussion only**, then asked to persist the research as prep for a future umbrella that will be designed with a stronger model.

This doc captures: (1) the idea in the operator's terms, (2) verification that we understood each other, (3) everything found in the repo that bears on it, (4) the one real gap, (5) conclusions + open questions for the next session. No design, no kickoff, no PR.

## §1. The operator's idea (verbatim intent, paraphrased)

**Pain.** In every new project the operator creates skills that "know" a specific tool at a specific version (React 19, Next 15, …). That knowledge is baked into the skill body. When the version moves, the skill rots and gets rewritten from scratch. Repeat per project, per tool, per version.

**Proposal.** Build **one (or two) universal skills** — (a) "work with rules / patterns / anti-patterns / best-practices / examples under a stack" and (b) "tests — write and verify generated tests per rule" — that **themselves know nothing about any specific stack/version**, and only know:

- the **data format** in which rules/patterns/anti-patterns/examples/tests are stored, and
- the **procedure** for reading that format and applying it to code.

The stack-specific content, in that format, is **regenerated by the framework per project** — because it rots anyway with new versions, and regeneration from live docs is the only freshness mechanism. The generator produces data in a format **tailored to be consumed by this universal skill**.

**Win.** Universal skill is static (one across all projects/versions). Stack knowledge is short-lived data (regenerated). No more rewriting skills per version — only regenerate data.

**Operator's own doubt.** *Is it even possible to separate "how to work" (universal procedure) from "what to work with" (stack specifics) via a single interface? Or is this fundamentally impossible — has the abstract fused with the concrete?*

## §2. Understanding verification (closed)

One ambiguity surfaced in the operator's phrasing — *"доставлять уже готовый скил, **который и генерировать это всё** в определённом формате"* — admitted two readings:

1. Universal skill = consumer only; a separate deterministic framework engine generates data (current repo pattern: `rule-research` skill → factory → JSON; skill reads JSON).
2. One universal skill does everything: fetches live docs, materializes into format, and works. No separate generator engine.
3. One universal skill, two roles: an author-mode (generates) and a work-mode (consumes).

Operator chose **"Два артефакта"** = option (1). Skill and generator are **two separate artifacts**. This matches how the repo already works. Understanding is verified; no further divergence.

### 4.5 Universal firing-test contract

Per-backend `firing-contract.json` — stack-agnostic data contract. Each backend ships one `[via Explore]`:
- `packages/core/backends/cargo/firing-contract.json`: `{"command": "cargo clippy --message-format=json", "jsonPath": "$.message.code.code", "expectedCode": "clippy::disallowed_methods"}`
- `packages/core/backends/ruff/firing-contract.json`: `{"command": "ruff check --output-format=json", "jsonPath": "$.code", "expectedCodes": ["TID251","TID253"]}`
- `packages/core/backends/astgrep/firing-contract.json`: `{"command": "ast-grep scan --json", "jsonPath": "$.ruleId", "expectedCode": "no-datetime-now"}`

Per-backend `firing-runner.ts` consume these; spec §5 explicitly says "we build no runner" — existing per-toolchain runners are borrowed.

### 4.6 Example of a thin stack-agnostic skill = `rule-research`

`.zcode/skills/rule-research/SKILL.md` is a ~31-line trigger over `agents/rule-researcher.md`. The agent **knows no stack** — it fetches live docs (context7/deepwiki/WebFetch with provenance tiers), materializes knowledge into two JSON files under the consumer repo's `.ai-factory/rules-research/`:
- `<stack>.research.json` — a `ResearchPlan` (`agents/rule-researcher.md:36-63`).
- `<stack>.selection.json` — a `GenerateSelection` of executable candidates (`agents/rule-researcher.md:66-95`).

A deterministic factory (`packages/core/synthesizer/rule-bootstrap.ts:6-9`) then consumes those files. The agent "never authors TypeScript or invents a rule the factory cannot prove fires" (`agents/rule-researcher.md:22`). This is **exactly** the operator's "two-artifact" pattern: thin skill = consumer, factory = generator, stack knowledge = data.

### 4.7 Stack knowledge = short-lived data (the anti-rot mechanism)

Three data shapes, all regenerable from live docs `[via Explore]`:
- `DetectionResult` (`packages/core/detector/types.ts:18-31`) — the detected stack profile.
- `ResearchPlan` / `GenerateSelection` JSON — researched practices per stack.
- `capability-matrix.json` per backend — e.g. `packages/core/backends/npm/capability-matrix.json` declares `syntax: yes` (with `evidence.kind === 'live-fired'`) and `type-aware: no (FF7001)`.
- `preset.meta.json` — per-preset pin snapshot with a `snapshotDate` and a staleness guard ("augment-first"; frozen preset is fallback). Example: `packages/preset-next-15-canonical/preset.meta.json`.

## §5. The main nuance — why the naive version of the idea trips

The operator's instinct "universal interface that abstracts stack differences" in its naive form is a **union-IR** and dies. The repo solves this with **narrow core + capability matrix**. Spec `2026-07-03-multi-toolchain-convention-compiler-design.md:32-58` `[via Explore]`:

> NOT an LLVM. **Narrow-core IR + per-backend capability negotiation** (the WASM/LSP survivor pattern; union-shaped universal IRs die — UAST, github/semantic, LSIF). **The capability matrix IS the architecture.**

Concretely — where ESLint cannot do type-aware analysis, the repo honestly writes `refused FF7001` rather than lying that "it works via the universal interface". Where clippy can do type-aware but it's not expressible in `clippy.toml`, it writes `degraded FF7003`. These divergences are **shown, not hidden**.

**The boundary, stated sharply:**

- **Procedurally abstractable — YES.** The pipeline `detect → research → synthesize → validate → install → render` is identical for any stack. This can and should live in one place.
- **Representationally abstractable — NO.** The real capabilities of each toolchain cannot be papered over. The capability matrix is what keeps the abstraction honest.

**Implication for the operator's idea:** universal skill is "universal procedurally", but it **must read the capability matrix** and surface where a backend said `refused`/`degraded` — not pretend all stacks do the same thing. This does not break the idea; it hardens it: the abstraction stays honest, not brittle.

## §6. The one real gap — "tests-skill" as invokable surface

The operator proposed two skills. Status:

| Skill | Status | Where |
|---|---|---|
| Rules / patterns / anti-patterns / best-practices under a stack | **EXISTS** | `rule-research` + composition/IR + 4 backends. Universal engine + stack data on input. |
| Tests — write/verify generated tests per rule | **GAP IN PACKAGING** | Capability exists in the factory; **no invokable skill surface**. |

For the tests-skill gap, **every primitive already exists** `[via Explore]`:

- Universal test format: `firing-contract.json` (`{command, jsonPath, expectedCode}`) — stack-agnostic.
- Per-backend runners: `packages/core/backends/{cargo,ruff,astgrep,npm}/firing-runner.ts`.
- Validator gates (npm L4): rule-tester (FF3005/3006), mutation gate (≥60% kill floor), tautology, conflict, single-token-diff, messageId-coverage, autofix-clean, require-vacuity — `packages/core/validator/` (8 gates per `architecture.md §2.6`).
- IR-level mandatory paired negative: `ConventionNode.pairedExamples.negative` (`ir/types.ts:39`).
- Mutation gate (npm-specific, declarative): `packages/core/audit-self/check-generated-rule-mutation.sh` + `packages/core/synthesizer/run-generated-rule-mutation.sh` — 11 deterministic selector perturbations, explicitly NOT Stryker/universalmutator.

What's missing: a skill an AI can invoke with *"write/verify the tests for this rule"*, orchestrating the above into one surface. The repo's own note (Explore): *"there is no skill named 'tests' that wraps this. The closest surfaces are `rule-research` (authors the test-bearing candidate) and `agents/rule-researcher.md` (the protocol). Packaging the verify-write-tests-per-rule step as its own skill would be new."*

## §7. Conclusions of this session (for the stronger model)

1. **The idea is sound** and is not a hypothesis — it is the working architecture of this repo. The operator independently re-derived the project's thesis.
2. **The "two artifacts" split is confirmed** — generator and consumer are separate; skill is a thin consumer; stack knowledge is short-lived data.
3. **One real action direction:** the "tests-skill" packaging gap (§6). All primitives exist; only the invokable skill surface is missing.
4. **Threads worth deepening** (not action, but needed before any design):
   - The unification trap (§5): why union-IR dies, why narrow-core + capability matrix survives, illustrated on FF7001/FF7003.
   - Thin skill vs fat skill: where exactly the "in skill" vs "in data" boundary sits — `rule-research` is the exemplar to study.
   - Staleness/regeneration mechanics: `augment-first` vs frozen-preset fallback, `deps-hash`, staleness guard — how these solve the operator's original "rewrite skills per version" pain.

- **Scope of the tests-skill.** Does it wrap **only** the verify/write-tests-per-rule step (small, low-risk, directly fills §6), or does it also subsume the rules/patterns surface (already covered by `rule-research`)? Recommend: scope it to the **gap only** (tests), do not duplicate `rule-research`.

- **"In skill" vs "in data" boundary for tests.** Mirroring §5's nuance for the tests-skill: what stays universal-procedural (test format, runner invocation, gate sequencing) vs what is stack-data (the `{command, jsonPath, expectedCode}` triple, the perturbation set). The `firing-contract.json` + `capability-matrix.json` pair is likely the seam — confirm by tracing a real render→test cycle end-to-end.
- **Does the tests-skill need to emit `ConventionNode`s?** The rule-research bridge still terminates at `SynthesizedRule` (npm-only) and has NOT been migrated onto the Convention IR (Explore finding §6 of agent 1: *"The rule-research bridge has NOT been migrated onto the Convention IR … the natural join point is named in the spec: a frontend (plane 1) that produces `ConventionNode`s from live research"*). If the tests-skill should be cross-toolchain from day one, this migration is a precondition — decide scope explicitly.
