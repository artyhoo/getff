The project has useful skill infrastructure: source ownership, generated copies, drift checks, context budgets, conditional references, explicit exclusions, and documented operational incidents. Its skills nevertheless need revision before a collection-wide compliance verdict. The most consequential problems are executable instructions that no longer match their helpers or consumer installations, and inaccurate statements about permission and mutation boundaries.

## Standards used

Requirements and recommendations are separate:

- [Agent Skills specification](https://agentskills.io/specification): required YAML metadata, naming and description bounds, directory alignment, resource conventions, and progressive disclosure. The 500-line and approximately 5,000-token entrypoint guidance is a recommendation, not a schema rejection threshold.
- [Anthropic skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices): concise task-specific instructions, conditional references, appropriate freedom, and evaluations based on realistic tasks.
- [Claude Code skill reference](https://code.claude.com/docs/en/skills): actual Claude Code frontmatter, invocation, permission and validation semantics. Claude-specific extensions are not automatically portable to other skill consumers.
- [OpenAI skill guidance](https://learn.chatgpt.com/docs/build-skills): focused capabilities, explicit inputs/outputs, deterministic helpers where appropriate, and checking description triggers.
- Local `skill-creator` guidance: preserve user scope, distinguish operational invariants from optional preferences, and avoid unnecessary procedural constraints.

Sources were fetched during this audit. No requirement was inferred that every skill needs `agents/openai.yaml`, `compatibility`, a script, a gerund name, or a particular directory layout. Those are optional or host-specific choices.

## Findings

### F1 Incorrect meaning of allowed-tools

**Evidence:** [.claude/skills/pipeline/SKILL.md:58](../../.claude/skills/pipeline/SKILL.md) says its `allowed-tools` list “constrains the skill” and excludes arbitrary Bash, then requires escalation for commands outside that list.

Claude Code documents `allowed-tools` as a grant allowing listed tools without a per-use approval request. Baseline permission settings continue to govern other tools; the field is not a deny list. See the [frontmatter and permission reference](https://code.claude.com/docs/en/skills).

**Failure-scenario:** a reader assumes that a skill cannot execute an unlisted command, or pauses useful work because the skill incorrectly treats an absent pre-approval as prohibition. The described boundary differs from the host's actual enforcement.

**Correction:** describe pre-approval accurately. If tool exclusion is required, point to the actual agent tool set or permission policy implementing it. Re-check the historical issue workaround before retaining it as a current requirement. Do not broaden global permissions merely to make this statement true.

### F2 Mutations included in a read-only diagnostic sweep

**Evidence:** [.claude/skills/aif-doctor/SKILL.md:49](../../.claude/skills/aif-doctor/SKILL.md) describes the ordered inventory as read-only; lines 54 and 58 include `verify-bridge.sh` and `ensure-parallel.ts`. Line 69 routes the “Read-only sweep” through that inventory.

The actual helper [verify-bridge.sh:8](../../packages/runtime-bridge/scripts/verify-bridge.sh) creates and deletes a task; line 98 explicitly warns that the coordinator may briefly start a real autonomous run. [ensure-parallel.ts:84](../../packages/runtime-bridge/src/cli/ensure-parallel.ts) writes project configuration through `putProject` when the flag is false. The skill's table acknowledges these effects but its overarching classification still calls them read-only.

**Failure-scenario:** an environment health investigation creates executable work or changes persistent project configuration before the skill has classified a needed repair. The mutation bypasses the skill's own advertised diagnostic/repair distinction.

**Correction:** separate passive probes from smoke dispatch and configuration repair. State each operation's effect and authorization conditions where it is selected; perform an active test only when the authorized task actually calls for it. Preserve the existing useful Tier-1/Tier-2 repair policy rather than adding blanket approval prompts.

### F3 Dispatcher example does not match its helper interface

**Evidence:** [.claude/skills/dispatcher/SKILL.md:285](../../.claude/skills/dispatcher/SKILL.md) invokes `harvest-via-api.sh <taskId> staging [path]`. The helper's [usage and parser](../../.claude/skills/dispatcher/helpers/harvest-via-api.sh) at lines 14–16 and 33–47 require `--repo`, `--base`, `--branch`, `--message`, and `--srcdir`.

Safe reproduction with placeholder arguments, rejected before any API call:

```text
bash .claude/skills/dispatcher/helpers/harvest-via-api.sh audit-task staging dummy.txt
exit 2
missing required flag (--repo/--base/--branch/--message/--srcdir)
```

The adjacent description also claims the helper reads from the container and is single-file; the current helper reads `--srcdir` and supports multiple paths. The sibling [harvest/SKILL.md:64](../../.claude/skills/harvest/SKILL.md) already shows the flag-based interface.

**Failure-scenario:** the documented recovery path fails precisely when normal git transport is unavailable, causing manual improvisation around an externally mutating workflow.

**Correction:** update the dispatcher instruction from the helper's actual interface and reference the shared harvest procedure. Verify the rendered command in an isolated test that stops before external writes.

### F4 Consumer skills require framework-only execution paths

**Evidence:** [plugin/skills/template-audit/SKILL.md:20](../../plugin/skills/template-audit/SKILL.md) requires `npm --prefix packages/core run test:template-render`. That script exists in the framework's [packages/core/package.json:63](../../packages/core/package.json), not in a generic consumer checkout or plugin payload.

[plugin/skills/rule-research/SKILL.md:22](../../plugin/skills/rule-research/SKILL.md) requires a framework source module; line 24 directs the agent to root `agents/rule-researcher.md` and `./setup --full`. [plugin/skills/rule-tests/SKILL.md:22](../../plugin/skills/rule-tests/SKILL.md) directs the agent to `agents/rule-test-author.md`. Neither agent is present in `plugin/agents/`; the installer delivers them under `.claude/agents/` ([setup.d/20-agents.sh:23](../../setup.d/20-agents.sh)).

The generator rewrites Markdown links, not bare code paths. Therefore local Markdown link checks passing does not make these runtime instructions usable. [plugin/README.md:27](../../plugin/README.md) records the decision to include these installer-bound skills and acknowledges the remaining prose. The installation command supplies an installation route; it does not make every framework source path available in the consumer root.

**Failure-scenario:** a plugin-only consumer invokes a shipped skill and cannot open its mandatory protocol or execute its first verification command. An installer consumer may have the protocol under a different path and is still instructed to use the framework path.

**Correction:** distinguish framework, installed-consumer, and plugin-only modes explicitly. Resolve protocols through their delivered locations; give a usable installation transition or an honest unavailable outcome when required enforcement is absent. Review the same source instructions before regenerating plugin copies.

### F5 Getff directs the agent to a missing React template

**Evidence:** [skills/getff/SKILL.md:90](../../skills/getff/SKILL.md) instructs React/Next workflows to load `templates/eslint.config.react.mjs`. That path is absent at repository root and in both getff skill directories. The table at line 71 correctly names `packages/preset-next-15-canonical/templates/eslint.config.react.mjs`.

**Failure-scenario:** an agent following the dedicated React workflow cannot load the prescribed source and substitutes remembered configuration for a template the skill promises is verified.

**Correction:** use the existing source location in framework mode and the actual delivered artifact in consumer mode. The generated plugin copy needs the corresponding delivery-aware wording, not only a link rewrite.

### F6 Seven frontmatters are not strict YAML

**Evidence:** PyYAML 6.0.3 and js-yaml 4.1.1 reject the description on line 3 of these source files:

```text
.claude/skills/aif-doctor/SKILL.md
.claude/skills/arch/SKILL.md
.claude/skills/claude-glm-executor-handoff/SKILL.md
.claude/skills/dispatcher/SKILL.md
.claude/skills/harvest/SKILL.md
.claude/skills/pipeline/SKILL.md
.claude/skills/tool-bootstrapping/SKILL.md
```

The cause is `: ` inside an unquoted plain scalar, for example `Triggers: ...`. The permissive project parser explicitly accepts this dialect ([48-skill-description-budget.ts:39](../../packages/core/principles/48-skill-description-budget.ts)).

**Counter-evidence:** Claude Code **2.1.286** reports `Validation passed` for `.claude/skills`, `skills`, and `plugin`. This finding does **not** assert that these skills currently fail to load in Claude Code or Codex.

**Failure-scenario:** a consumer using strict YAML tooling cannot validate or package these source skills under the open format despite the project-specific parser passing them.

**Correction:** quote or use a folded block scalar for these descriptions. Retain Claude extensions where their channel supports them; do not confuse valid host-specific fields with invalid YAML syntax.

### F7 Large entrypoints defeat progressive disclosure

**Evidence:** measurements of entrypoint bodies, excluding frontmatter:

| Skill | Body lines | Body words |
| --- | ---: | ---: |
| pipeline | 582 | 8,286 |
| dispatcher | 508 | 6,132 |
| aif-doctor | 381 | 8,780 |
| orchestrator | 486 | 5,802 |
| arch | 165 | 4,302 |
| night-mode | 66 | 3,171 |

`pipeline` and `dispatcher` exceed the 500-line recommendation. Dense paragraphs and padded tables mean line count alone understates context cost: `aif-doctor` has the most words despite staying below 500 lines. Word counts are not token measurements.

**Failure-scenario:** activating an ordinary submode loads historical incidents, broad runbooks, and conditional protocols that compete with task context, increasing the chance that the relevant branch is overlooked. This is a best-practice risk; no performance loss was measured here.

**Correction:** retain routing, essential invariants and outcome contracts in the entrypoint. Move mode-specific catalogues, historical evidence and detailed tables into clearly routed references. Preserve non-obvious operational constraints; do not shorten merely to reach a number. The short `rule-tests` and `rule-research` wrappers demonstrate useful source delegation, although F4 must be fixed to make that delegation executable for consumers.

### F8 Bootstrap instruction priority and fallback are ambiguous

**Evidence:** [plugin/skills/using-getff/SKILL.md:17](../../plugin/skills/using-getff/SKILL.md) puts project/user instructions first, skills second and “Default system behaviour” last. Line 27 prohibits reading a skill with the Read tool to use it. Line 25 uses a 1% applicability threshold, and the description activates at the beginning of any conversation.

**Failure-scenario:** a host without a Skill tool cannot follow the bootstrap's proposed fallback, or an agent reads “default system behaviour” as permission to demote binding system/tool constraints. The text does not prove that any actual host restriction can be bypassed.

**Correction:** make clear that binding host/system/tool rules retain their priority and that the ladder concerns overridable defaults. Permit direct file reading where that is the harness's skill mechanism. Consider a scope-based trigger for unrelated conversations; retain broad startup invocation if it is a deliberate product requirement rather than calling it a universal standard.

### F9 Routing quality remains unverified by the passing checks

**Evidence:** [15-skill-paired-negative.test.ts:9](../../packages/core/principles/15-skill-paired-negative.test.ts) defines its checks as structural presence. Its implementation checks headings, minimum text length and unequal halves. [48-skill-description-budget.test.ts:8](../../packages/core/principles/48-skill-description-budget.test.ts) expressly distinguishes budget checks from description routing quality. `tests/plugin/skill-routing.test.sh` tests companion routing configuration, not a model choosing among this collection's descriptions.

Potential collision examples include the generic `audit`, `template`, and `AGENTS.md` terms in `template-audit`; `skills` discovery in tool-bootstrapping; broad getff triggers; and the startup catchall in using-getff. These are **hypotheses**, not observed misrouting incidents. The [local description discipline](../../.claude/rules/skill-description-quality.md) correctly records semantic quality as deferred rather than claiming a structural proxy proves it.

**Failure-scenario:** passing generation, drift and narrative checks is treated as proof that a skill activates correctly and improves decisions, while a wrong skill captures a request or a relevant skill is skipped.

**Correction:** use representative positive, negative and neighboring requests to evaluate selection and resulting behavior. Prefer a small existing session-bound evaluation approach over adding word-count or heading proxies. Any deployment of a new semantic gate remains a separate decision; this audit does not supersede the incident-driven local policy.

## Addendum — 2026-10-05: thin cards and the 200-unit distinction

The operator explicitly requested this report update and subsequently authorized repairs. The original findings and evidence above remain the audit snapshot; this addendum records the clarified repair direction.

**Verified guidance:** the [Agent Skills specification](https://agentskills.io/specification#progressive-disclosure) recommends an entrypoint below 500 lines and approximately 5,000 tokens; these are recommendations, not universal schema rejection limits. [Anthropic](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices#progressive-disclosure-patterns) also recommends under 500 lines. This is an upper orientation, not a desirable card size.

The [Superpowers writing-skills guidance](https://github.com/openai/plugins/blob/main/plugins/superpowers/skills/writing-skills/SKILL.md) targets fewer than **200 words** for frequently loaded skills, not 200 lines. A [separate marketplace's guidance](https://github.com/jeremylongshore/tons-of-skills-marketplace/wiki/SKILL-md-Specification#line-budgets) uses **200 lines** as its optimal body budget. Its grading rules are not the open specification. For these repairs, use **a concise card, normally at most 200 body lines**, as a working target; do not introduce a universal hard gate or pack long paragraphs to satisfy the count.

The agreed structure is:

| Layer | Contents |
| --- | --- |
| `name` + `description` | Capability and precise selection conditions |
| `SKILL.md` | Inputs, output, main actions, required constraints and stopping conditions |
| `references/`, `scripts/`, `assets/` | Detailed procedures, separate modes, examples, executable helpers and templates, loaded when needed |

The specification describes loading the full entrypoint on activation. Moving details below the first 200 lines in the same file therefore does not provide progressive disclosure. Each extracted reference needs an explicit condition in the card, such as “For recovery after an error, read `references/recovery.md`.” Requiring every appendix on every invocation eliminates the intended context saving. Keep references directly discoverable from the card and constraints available before the relevant action; a short standalone skill needs no artificial supporting files.

F7 particularly concerns `pipeline`, `dispatcher`, `aif-doctor` and `orchestrator`. Extract incident history, large catalogues and mode procedures. Also inspect dense `arch` and `night-mode`: their short line counts conceal substantial context cost. Preserve operational invariants and verify paths and delivery contracts after extraction. F1–F6 remain concrete repair priorities; F8 needs clarification and F9 requires honest behavioral evidence, not a line-count proxy.
