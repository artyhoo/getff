# M04: actual installed default configuration contract

The P53 case `A04: actual installer preserves approved default preset artifacts`
runs the actual non-full installer in three fresh temporary Git consumers:
`ts-server`, `react-next`, and `react-spa`. It requires native installer success,
an actual placed `eslint.config.mjs`, and its independently approved literal hash
from `frozen-installed-contract.json`. Empty, duplicated, or missing profiles fail
the exact population assertion. The existing P53 `sha256File` measures placed bytes.

This is an additional structural identity check in the existing principle lane.
The existing fifteen-cell installer fingerprint gate already runs in CI; its
baselines and the cheaper pre-push staleness check remain separate protections.
This case adds explicit installer status admission and the three approved defaults.

The literal expectations were frozen before this implementation and follow the
accepted M08 and E917 actual installed configuration and diagnostic evidence.
They are never computed from the current producer or installer output. Exact
artifact identity permits reuse of that bounded evidence; it does not establish
general runtime semantics, arbitrary consumer configuration validity, or a new
severity policy. Numeric severity support and kept consumer configurations retain
their existing contracts. Expo and bare React Native remain in their named manual
scope.

A legitimate default configuration change requires independent expectation review
and affected semantic evidence. Updating a hash to follow a faulty template is not
an accepted repair. This increment does not change snapshot baselines or install
dependencies, invoke research or models, or run the full installation capstone.

The selected-case controls execute one case and intentionally filter thirteen other
P53 cases. The full affected P52/P53 run is a separate thirty-case obligation.
Evidence must distinguish those populations and retain actual installer statuses,
physical hashes, durations, and complete output. A first-profile failure does not
credit the two later profiles as executed.

The original final-cycle controls require healthy/fault/restored canonical exits
`0/1/0` for the actual ts-server Q1 severity-off edge, while the installer itself
returns zero and places the independently known bad artifact. Comparing the actual
hash to itself must be caught by the fixed external oracle; inverting the comparison
must similarly fail healthy admission. Both source and checker are restored exactly
before the complete affected suite and normal hooked source candidate commit.

Actual selected canonical exits were `0/1/0`; all reached installers returned zero.
The faulty installed ts-server configuration had SHA256
`615587f676092ef25e6668a1d2984381b906543f8183f37b9f01530f48c16ec4`
and failed the intended placed-artifact assertion. The self-comparison wrongly
admitted those bytes, while the inverted comparison rejected the approved bytes;
the unchanged external observer rejected both checker faults. All source, checker,
protected inputs, and literal expectations were restored exactly afterward.

The initial baseline and restored selected runs took 55.483 and 52.815 seconds.
These observations record repair overhead for the separate S3 evaluation; they are
not a comparable workload campaign or performance acceptance. The first external
observer initially misread Vitest's per-assertion `skipped` label for thirteen
intentionally filtered cases. Its failed observation and native report are retained.
A corrected observer reconciles that label with `numPendingTests`; it reused the
same actual baseline without rerunning it and was frozen before any fault control.
The independent byte and process oracles were never changed.
