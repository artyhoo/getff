# /night-mode — thin overnight layer over subagent-driven-development

Run a well-scoped implementation task to completion with **no human in the loop**. The dispatch loop — a coordinator dispatching a fresh implementer per increment, then SDD's review seats, with a rework loop to convergence — **is `superpowers:subagent-driven-development` (SDD)**. Use it. This skill adds **only** what SDD does not cover for an _unsupervised overnight_ run. If you catch yourself re-describing the executor/reviewer roster or the review loop, stop — that is SDD's job, and re-describing it is the `#parallel-evolution-creep` this project exists to prevent.

## The loop is SDD (do not reinvent)

Invoke `superpowers:subagent-driven-development` for the core: coordinator → fresh implementer subagent per increment → SDD's per-task reviewer(s) + final whole-branch code reviewer → rework loop. **SDD owns the implement→review→rework loop and its reviewer roster** — point at it for role contents; this skill does not re-describe either. **Overnight model posture — relative capability tiers, not hard-coded model names** (so it degrades across harnesses and model sets exactly as SDD's «least powerful model per role» does — this subordinates to that framework, does not re-describe it). Assign each role a tier, then fill it with whatever the active harness offers: **top tier → advisor + SDD's final whole-branch review** (Claude: Fable) — SDD dispatches that review on the most capable available model rather than the session default, so it sits at the top of whatever window is in play; **review tier → SDD's per-task review seat** (Claude: Opus) — the review layer is the quality safety net over the executor; **executor tier → implementer + fix subagents** (Claude in-session: Sonnet; inside the aif factory: GLM) — the same executor tier `packages/core/templates/shared/tier-home.md` §2 names, so do not raise implementer or fix subagents to the review tier «for quality» and do not flag an executor-tier implementer as a miss (operator directive 2026-07-21, #931 SDD run; parity gate in the source repo: `packages/core/principles/49-executor-tier-parity.test.ts`). The window **slides** to the available set — Claude with no Fable → [advisor + review Opus, executor Sonnet]; another harness (e.g. GLM/zcode) → [its most-capable, its mid, its cheap]. If a harness exposes only ONE model tier, the advisor collapses to a **fresh-context same-tier second opinion** (a different context catches different things — not a stronger model), or is skipped. A per-session tier override (e.g. «drop mechanical increments to the cheapest tier (Claude: Haiku)», «no advisor this run») is stated at launch. Advisor-consult mechanism: delta item 7.

> **Harness portability — agnostic with graceful degradation (NOT CC-only).** The loop needs only **sequential subagent dispatch**, which exists on CC AND on zcode/GLM — verified 2026-07-04: `~/.zcode/cli/agents/` holds real subagent sessions, `~/.zcode/cli/artifacts/sess_subagent_agent_*` are dispatches that ran, and zcode ships a **Settings → Subagents** surface. The CC-named primitives this delta uses are **capabilities with portable fallbacks**, not hard requirements: `Workflow` (context-economy) → keep the summaries-only discipline by hand where there is no Workflow tool; `ScheduleWakeup` (quota-backoff) → the harness's own sleep/resume, or a manual resume; `isolation:"worktree"` (parallel executors on disjoint files) → run **sequential** where the harness has no parallel subagents (zcode dispatches subagents but not in parallel — `skill-creator/SKILL.md:101`), which is SDD's default anyway; subagent **hooks** (digest/report injection) are absent on zcode (its event set has no `SubagentStart`/`SubagentStop`) → carry that discipline in the dispatch prompt instead. **Net: night-mode is _designed_ to run on any harness with sequential subagent dispatch; only the parallel-executor speedup and hook-based context-hygiene degrade.** The _precondition_ (zcode has sequential subagents) is verified 2026-07-04, but an end-to-end night-mode run on a non-CC harness is **not yet exercised** — per this skill's own §5, treat portability as _designed-not-proven_ until a live probe. It _targets_ the portable-with-graceful-degradation bar that `pipeline`/`dispatcher` meet **by test** (principle 21); night-mode has no such conformance test yet. Consumer-facing default = dual / graceful-degradation ([dual-implementation-discipline.md §2/§3](../../../rules/dual-implementation-discipline.md)).
