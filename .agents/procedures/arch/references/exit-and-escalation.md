## §3 Phase 3 — exit routing (delta #2)

**Kill channels, enumerated with their cost ordering.** An idea can die at: the research-spec (pre-mortem) → the distillate (idea verdict) → the critique (REVISE/STOP) → acceptance. Each cheaper than the next. The last two are judged by a seat **cold as defined in §2**; the distillate verdict is not — §1.5 step 3 has the verifier seat distil _and_ rule on its own distillate, which is exactly why §1.5 step 4 puts a **cold** K-pass over that artifact before anything consumes it. The contour's job is to make the cheap deaths _reachable_ — the project's «fails at the earliest reachable channel» thesis ([README.md#why-this-exists](../../../../README.md#why-this-exists)) applied to ideas.

Two decisions, in order — this is the contour's boundary:

**Decision 1 — factory or in-session?** A senior judgment this skill owns (it is NOT part of the CLAUDE.md tier table, which governs only the factory path). Factory is the **default** for bulky work. Keep it in-session when the work needs the operator in the loop as it unfolds (discipline-bearing authoring, live design iteration), touches surfaces the factory cannot write (agent-uncommittable globals), or the contour itself produced it small enough to finish here.

**Decision 2 — route:**

**Plan-preparation guard for feature work with recorded intent continuity (2026-10-12, intent-continuity slice A1).** Before an executable handoff is prepared on either route — factory kickoff authoring or in-session `writing-plans` — for work whose feature has recorded intent continuity, the independently selected current authority must pass:

`node .agents/procedures/intent/helpers/current-decisions.mjs --check-plan-prep --feature <feature-id> [--spec <exact-spec-path>] --orch-home "$(bash .agents/procedures/pipeline/helpers/print-orch-home.sh)"`

Exit 0 requires the selector's current PRD approval, the exact operator-agreed spec bound to that PRD (live-resolving content refs), and a current `matches` attempt over those same bytes; `--spec` additionally pins that the bytes being handed off digest to the agreed spec (`spec_bytes_mismatch` otherwise). Exit 2 holds the handoff — missing/changed PRD approval, unagreed or superseded spec, stale review: repair the evidence, never route around the gate. Work with NO selector entry keeps its current (legacy) route unchanged — do not improvise a selector entry to force a pass; whether a pre-existing artifact is legacy is answered by the admission freeze, not by judgment: `--classify-artifact --path <abs>` returns `frozen-legacy` (frozen before the upgraded path activated) or `unknown` (adoption required first), and holds with `freeze_missing` when no freeze exists yet — `--freeze-legacy` creates it, write-once. The feature/stage identity that gates adopted work is durable and lives outside any editable kickoff — the feature ID recorded with the intent decision artifacts — so deleting a kickoff or its marker cannot reclassify adopted work as legacy.

**Dispatch chips at the exit (ADR D1/D2, stage S1 — the contract is owned by [pipeline `references/output-format.md §9`](../../pipeline/references/output-format.md), never restated here).** **Launch card at the exit (plain-words-recap-v2 D7 — contract owned by [`references/output-format.md §9A`](../../pipeline/references/output-format.md), never restated here):** alongside the chips, the exit emits the launch card — recommended channel + arguments + plain-words explanation + ready artefacts per channel, routed by the two card questions; the operator picks. When `spawn_task` is invocable in this session, emit one chip per routed next action from the table above, ALONGSIDE the written handoff — **except** the single-task `bridge: auto` row: the write-time hook `.claude/hooks/runtime-bridge-dispatch.sh` (factory depth only — the runtime-bridge vendor drop) already dispatches that kickoff, so a chip there is a second dispatch path for the same task. Each chip prompt carries the same four steps — `Isolation first` → `In-flight probe` → `Stage-gate at click time` → cwd + artefact path — and is rendered in full next to the chip. Chips are additive and ephemeral; the routed artefact (kickoff on staging, or the in-session plan) stays the durable record. **Before any chip, try aif auto-dispatch** — the §9 «Channel order»: with the bridge up and no unmet gate, a routed kickoff goes out through aif and the exit reports it running; a chip is emitted only for the cases §9 lists, named in a `chip-over-bridge:` line.

**Product-discussion exit.** When the dialogue surfaced product-level decisions that belong to the product contour rather than this one — an agreed brief waiting for approval, a promise the first result must be judged against, or a route here that should have been the product contour — the exit hands them to the intent advisor (the product-only seat prepared per [`../../intent/SKILL.md`](../../intent/SKILL.md)) instead of folding them into a factory kickoff. The review protocol, record shapes and publication rules that advisor follows are owned by the `/intent` contour's own references — never restated here.

## §4 Escalation intake (the contour's return edge)

Factory tasks park questions (runtime-bridge `park`/`answer`). Sweep them in batch from a top-tier session («office hours»): in-scope architecture questions → the senior-executor seat answers; intent/goal/creative questions — and anything the senior seat is unsure about — → the top seat. Route by question class, not by a fixed hop chain. **Review-`ESCALATED` intake (2026-08-10):** findings graded `ESCALATED` by any §2 review seat (unrecorded value premise) arrive on this same edge — they route to the concept holder (the advisor seat, [advisor-pattern-design §3/§6](../../../../docs/superpowers/specs/2026-08-10-advisor-pattern-design.md)); floored objects go to the operator with a pre-built decision package.

For an adopted intent-continuity ask in the existing mailbox, use the class named by its `target` directly: `task` reads the bound kickoff/plan, `architecture` the current agreed spec, and `intent` the current approved PRD with a fresh artifact-only responsibility. Before taking an answered ask back to the task owner, run `bash scripts/check-ask-files.sh --accept-adopted <ask-file>` from the project root; its exit 2 holds application. For `task`, this command re-fetches `GET /tasks/:id` and verifies the active ID and persisted kickoff/plan bytes. The journal entry must bind that exact ask and return owner (and `task-id` for task). A passing answer cannot change an operator-owned product promise or replace the agreed spec; those forks return to the corresponding written discussion.
